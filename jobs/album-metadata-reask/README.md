# album-metadata-reask

One-shot job that re-asks LML for `album_metadata` rows whose stored Discogs release disagrees with the catalog card's current LML pin (`pin_mismatch`), or still serves a pin that the pin review removed (`pin_removed`). It is step 3 of the `album_metadata` remediation; the plan, decisions and slices are on the tracker, [WXYC/Backend-Service#3137](https://github.com/WXYC/Backend-Service/issues/3137).

## Status

In progress. With no flags the job runs the dry run (below): it reads, and it never calls LML or writes. `--preview` asks LML for a sample and writes nothing. `--catalog-pass <run_id>` runs the catalog cover pass alone, and `--restore <run_id>` restores a run's writes (all below). `--execute` (outside `--restore`) refuses with the issue that builds it, before any file is read, and exits 1. Any other unknown flag also refuses; `--dry-run` is accepted and changes nothing.

## The album write

One statement per album (decision 7 on #3137). It locks the `album_metadata` row only while its `discogs_url` still equals the value the cohort read (the race guard), inserts one `album_metadata_reask_backup` row with before and after images of the 13 release- and artist-group columns and the provenance, and updates the row with `updated_at = NOW()`. The backup row and the update commit together or not at all, and the backup's `written_at` equals the row's new `updated_at`. Zero rows back is `skipped_raced`.

- **Release group** (`discogs_url`, `artwork_url`, `release_year`, `label`, `full_release_date`, `genres`, `styles`, `tracklist`): written as a unit from the answer, nulls included; all NULL on `clear` (decision 3).
- **Artist group** (`discogs_artist_id`, `artist_bio`, `artist_wikipedia_url`, `artist_image_url`, `bio_tokens`): `artist-keep-sql.ts`, decision 8. A null in the answer keeps the stored value only when both `discogs_artist_id`s are set and equal; otherwise the answer is written, nulls included. Kept as stored on `clear`, and still imaged, so a restore never meets a missing key. `artist_cleared` counts a stored bio replaced by none.
- **Never written:** the streaming columns, and `library`. The catalog cover is the catalog cover pass's (below), so the catalog watermark moves once per run, not once per album.

`runBatch` asks LML with `allowReleaseResolutionFallback: true` and `budgetMs: null`, decides each admitted row with `decideReask`, and writes only `rebind`, `rebind_unpinned` and `clear`. A failed bulk call carries the whole batch; a write that throws carries its album.

## The catalog cover pass

`library.artwork_url` is served by catalog search and copied into `library.db`, and every other writer to it is fill-null, so a wrong-release catalog cover never heals on its own (BS#2258). Decision 4 on #3137: the pass rewrites it only where it still equals the cover the album write replaced. A catalog cover that differs came from a librarian or another backfill and is never touched.

The pass reads one run's `album_metadata` backup rows. It skips an album whose stored release or cover changed since the write (`album_metadata.discogs_url` or `artwork_url` is distinct from the `after_image`'s), that already has a `library` backup row for the run, or that a restore of the run put back (a `restore` marker). For the rest it sets `library.artwork_url` to the backup's `after_image->>'artwork_url'` (NULL for a `clear` or a coverless release) where the catalog cover is non-null, equals `before_image->>'artwork_url'`, and differs from the new cover. One statement writes every `library` backup row (`target_table = 'library'`, the album write's provenance) and updates only the rows it backed up.

- **The guard is the release and cover, not `updated_at`** ([#3274](https://github.com/WXYC/Backend-Service/issues/3274)). The bio fill, the streaming drains and the enrichment worker's UPSERT bump `updated_at` without touching either. Under an `updated_at` guard, an album any of them touched between the album write and the pass would never get its catalog cover fixed, which matters for a `--catalog-pass` run later for a run that died. The pass only needs the stored release and cover to still be the ones the re-ask wrote. The release check matters for a `clear` or a coverless release, where any later NULL cover would otherwise match. Restore keeps the stricter `updated_at` guard (below), because it must not undo anything changed since the write. So a catalog cover the pass rewrote after such a touch cannot be restored: restore counts it in `library.backed_up` but not in `restorable`.
- **One statement per run.** The catalog watermark trigger `touch_library_watermark` (migration 0185) is `FOR EACH STATEMENT` and fires even on a zero-row UPDATE, and each bump makes every client re-download the catalog (BS#2052). So the pass first sends a read-only probe of the same rows and sends the write only when the probe finds some. An empty probe sends nothing and leaves the watermark alone.
- Probe and write run in one transaction under `SET LOCAL statement_timeout` from `REASK_CATALOG_STATEMENT_TIMEOUT_MS` (default 30 s). The write locks both the `album_metadata` and the `library` rows, so a row another writer commits during the pass is checked again on its latest version. After a pass that wrote, the job runs `ANALYZE wxyc_schema.library` in its own transaction under the same timeout. If that fails, the job logs `analyze_pending` and still reports the counts, because the rewrite has already committed and a rerun would find nothing to do. Run the ANALYZE by hand.
- **Side effects, accepted:** one watermark bump per pass that writes, and one row-level `cdc_library` `pg_notify` per rewritten row (migration 0046).
- **Idempotent.** A second pass for the same run finds nothing: each rewritten album has its `library` backup row.
- `--catalog-pass <run_id>` runs the pass alone, for a run that died before its end. It reads no input file and takes no other flag. It trims the `run_id` and logs one `catalog_pass` line with `album_writes`, `probed` and `rewritten`. A `run_id` with no album writes (a typo) is an error and exits 1. The execute loop ([#3151](https://github.com/WXYC/Backend-Service/issues/3151)) will call the same function at the end of each run.

## Restore

Decision 7 on #3137: every write can be reversed from the backup table, skipping rows changed since. `--restore <run_id>` counts per target and writes nothing; add `--execute` to write, and `--album-ids <ids>` (up to 200, comma-separated) to restore only those albums. It reads no input file and accepts no other flag; `REASK_ALBUM_IDS` is refused with it, so the dry run's knob cannot look like it narrows a restore. Do not restore a run while another run is in progress: a run that enumerated an album before the restore committed would still write it, because the hold is applied at enumeration. A `run_id` with no album writes in scope (a typo) is an error and exits 1. The counts go on one `restore_plan` line (dry run) or `restore` line (execute): per target, `backed_up` (the run's backup rows in scope), `restorable` (rows the guards still allow) and `restored`.

- **The guard.** An album is restored only while its `album_metadata.updated_at` still equals the `written_at` of its own `album_metadata` backup row for the run. Every writer bumps `updated_at`, so any change since the re-ask's write, by anyone, keeps the album as it is now, and keeps its catalog cover too. A catalog cover is restored only while it still equals the cover the pass wrote (`after_image->>'artwork_url'`), so a cover a librarian set after the pass is kept.
- **Two statements, one transaction.** The `library` statement first sets each catalog cover back to its `before_image`. Then the `album_metadata` statement sets the 13 imaged columns back with `jsonb_populate_record` over the `before_image` (which always holds all 13, so a `clear` row's artist group comes back exactly) and bumps `updated_at`. `album_metadata` goes last because that bump ends the library statement's guard. Each statement is sent only when a read-only probe in the same transaction finds rows for it, so a run with no catalog cover to restore leaves the catalog watermark alone. The transaction runs under `SET LOCAL statement_timeout` from `REASK_RESTORE_STATEMENT_TIMEOUT_MS` (default 5 minutes). After it, the job runs `ANALYZE` on each table it wrote, in its own transaction; a failure is logged as `analyze_pending`, naming the table, the counts are still reported, and the other table is still analyzed.
- **The marker.** The `album_metadata` statement also inserts one backup row per restored album with `target_table = 'restore'`: `before_image` is the job's after-image, `after_image` is the restored image, and `provenance` holds `restored_run_id` and the restored write's provenance. The cohort enumeration flags any album with a marker (from any run) as `restored`, and admission holds it as `hold_restored`, counted in the dry run and listed on a `held_restored` line. `REASK_INCLUDE_RESTORED=1` lifts the hold, for the canary's deliberate re-run of its restored album and for a re-ask the owner chooses after fixing the cause.
- **Idempotent.** A second restore of the same run restores nothing: each restored album's `updated_at` has moved on.
- The flowsheet has no restore target: the flowsheet inline-nulls slice (#3149) was closed as superseded by #3168.

## Preview (the sign-off sample)

`--preview` is the sign-off artifact the owner (and the music director, if he wants) reads before any `--execute` (#3137, "Dry run, preview, and sign-off"). It needs `REASK_SAMPLE_SEED` and `REASK_MAX_ALBUMS` (the sample size; 200 is the plan's size), and takes the dry run's other knobs. It writes nothing: `runBatch` runs with `write: null`, and the only statements are the cohort reads and one read of the sampled rows, each under `REASK_READ_TIMEOUT_MS`. A unit test renders every statement and refuses any write.

- **The sample.** Every admitted album under the cursor and list (no cap) is the population; the admission rule is the dry run's, so a `hold_restored` album is held unless `REASK_INCLUDE_RESTORED=1`. Strata are `reason` and pin source. The strata are taken round robin, in an order the seed shuffles, each stratum shuffled by the seed, so a small stratum is in the sample whole before a large one takes more than an equal share. The same seed and population give the same sample.
- **The ask.** Batches of `REASK_BULK_BATCH_SIZE` at `REASK_BULK_RATE_PER_MIN`, through `runBatch` and `decideReask`, as `--execute` will ask: the fallback flag on and no budget header. No streak aborts; an album LML did not answer is listed as `indeterminate`, and if LML answered none of the sample the job exits 1 after the lines, so a dead LML cannot pass for a sign-off sample.
- **The output.** One `preview` log line per album, then a `preview_done` line with the verdict totals. Keep the lines with `jq -c 'select(.step == "preview")'`. Each line has `album_id`, `card` (the catalog card id), `artist`, `title`, `reason`, `tier`, `stored_release` (id and URL; Backend does not store a release title), `pin` (release id, source and, for `pin_removed`, the expected release), `lml_release` (the top result's release id and title as LML answered it, whatever the verdict; null when LML returned no match, and id 0 for LML's synthetic streaming-only answer) and `verdict`. A would-be write (`rebind`, `rebind_unpinned`, `clear`) also has the fields below; if its `album_metadata` row is gone by the time of the stored read, it has `changes: null` and nothing else.
  - `changes`: each of the 13 written columns whose value would change, `{ old, new }`. `tracklist` and `bio_tokens` are shown as their lengths, so a line stays under Docker's 16 KB log-line limit. The artist group follows the write's rule (decision 8), and `clear` keeps it.
  - `catalog_cover`: the catalog cover pass's rewrite, `{ old, new }`, or null when the catalog cover does not mirror the stored one.
  - `streaming_links_equal`: whether the answer's five streaming links, as the enrichment would store them, equal the stored ones. The job never writes them; a false here goes to the owner before the canary. Null for `clear`.
  - `artist_cleared`: a stored bio the write would replace with none.
  - `null_cover_sibling`: for a NULL new cover, whether another album with a cover shares a lookup key with one of this album's plays. `/playlists/recentEntries?v=2` (`enrichPlaycuts`) would show that album's cover. It reads the siblings' covers as they are now, so a sibling this run will also rewrite still counts. Null when the new cover is not NULL.

There is no flowsheet pass (#3149 was superseded by #3168), so the lines carry no per-column play counts.

## Build and deploy

- `"job-type": "one-shot"`: no schedule.
- `deploy-base.yml` builds and pushes the image on any push to `main` that changes this directory or `Dockerfile.album-metadata-reask`. Until the run loop lands, that image writes only through `--catalog-pass` and `--restore --execute`.
- Local build: `npm run build --workspace=jobs/album-metadata-reask`. Typecheck: `npm run typecheck --workspace=jobs/album-metadata-reask` (also a CI step, since the root typecheck skips `jobs/**`).

## Input files

`inputs.ts` ([#3141](https://github.com/WXYC/Backend-Service/issues/3141)) parses the three files the run reads. Each must have exactly this header, in this order; every id is a positive integer, no `library_id` repeats, and any line that does not parse refuses the whole file (an empty required value is an error, never a default). A leading BOM, CRLF and a missing final newline are tolerated; quoted values, surrounding whitespace and non-UTF-8 bytes are not. The parser returns each file's SHA-256 and row count for the run log.

| File             | Header                                                                                                                                                                                           | Notes                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pin export       | `library_id,discogs_release_id,source,updated_at`                                                                                                                                                | The `\copy` of `lml_cache.library_release_override`. Must have at least one row.                                                                                                                                                                                                                                                                                                             |
| Removal file     | `library_id,discogs_release_id,source`                                                                                                                                                           | Step 2's removed pins whose card has no pin now. May be empty.                                                                                                                                                                                                                                                                                                                               |
| Grading manifest | `library_id,stored_release_id,pin_release_id,pin_source,stored_title_score,pin_title_score,stored_play_rate,pin_play_rate,excluded_other_plays,excluded_inferred_plays,tier,expected_release_id` | Written by the offline grading tooling. Grades are unsigned decimals, empty when the axis cannot grade. The excluded-play counts are required. `tier` is one of `rebind`, `hold_stored_better`, `hold_ungradeable`, `hold_manual`. `expected_release_id` is set only on tier-1 `pin_removed` rows. For a `pin_removed` row, `pin_release_id` is the removed pin. Must have at least one row. |

`admit(row, manifest)` is the admission rule (decision 2 on #3137). A `pin_mismatch` row is asked if its tier is `rebind`, or `hold_ungradeable` with pin source exactly `alex-l-2026`. A `pin_removed` row is asked unless its tier is `hold_manual`. A card missing from the manifest is held as `hold_unmanifested`. A card whose manifest entry graded other releases than the row now has is held as `hold_manifest_stale`. Before all of these, an album a restore put back is held as `hold_restored` unless `REASK_INCLUDE_RESTORED=1`.

## Dry run and knobs

The dry run is the default and makes zero LML calls and zero writes. It parses the three input files (and refuses before any database read if one is malformed), logs each file's SHA-256 and row count (`inputs`), counts the whole cohort, enumerates the drainable rows under the cursor, cap and list, applies `admit`, and logs one `dry_run_plan` line: the cohort counts by reason and pin source, the excluded counts by cause (`no_artist_name`, `discogs_unavailable`, `removed_stores_other`), the catalog covers that mirror the stored cover, the admission (asked, the `alex-l-2026` ungradeable exception, held by tier) and the batch count over the asked rows. Compare the cohort count with the plan's Q2 sizing by hand.

Every knob that is set must parse; a value that does not is an error, never a default. The env parsers are copied from `album-metadata-bio-fill` (decision 6).
