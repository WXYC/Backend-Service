# Intake and reviews

Route and rule reference for `/intake` and `/reviews`, moved out of `CLAUDE.md`'s route table so slices that touch different routes do not conflict on one line. Add a new rule as its own bullet; keep one rule per line.

## `/intake`

- DJ album-review intake (BS#2796): log, list, get, patch, delete.
- Role-gated `reviews:read` (dj+) for reads, `reviews:manage` (MD+) for log/patch/delete.
- `GET` filters on **effective state** (an expired `requested`, or one whose DJ account is gone, reads as `pool`; a checkout more than 14 days old is `overdue`, checked out or reviewed alike), defined once in `services/intake.service.ts`; reads never write.
- `passes` only for `reviews:manage` callers. 409 `already_filed` on patch/delete once filed.
- BS#3052: `requested_dj_name`, `checked_out_by_name` and `passes[].dj_name` are `staffNameSql` over the joined account (the real name, else `auth_user.name`), computed per read and never stored, so they change as soon as an account's `real_name` does; a deleted account is still `null`. Every `reviews:read` caller sees them. `draft_authors` is unchanged: the stored `reviews.author` text.
- BS#2797: PATCH sets or clears a citation (`cited_album_id` / `cited_submission_id`; setting one clears the other); both non-null is a 400 (controller and service); an invalid or nonexistent citation is 409 `invalid_citation`; refusal order is `not_found`, then `already_filed`, then `invalid_citation`.
- BS#2860: a PATCH that changes the stored `cited_album_id` (another release, null, or a submission cited instead) also takes off a review accepted through the citation (not the item's own) with the exported `RELEASE_ACCEPTED_REVIEW` `SET`, whose `CASE` tests `checked_out_at` (a checkout with a deleted holder returns to `checked_out`, not `pool`); `POST /intake/{id}/accept-review` (`reviews:manage`, body `{ review_id }`; its own function `acceptReview`, not a `TRANSITIONS` entry) accepts one submitted review of the record (its own, the release it was filed as, or a typed review of its cited release), locking the cited release `FOR SHARE`, then the item, then the review; `release` also returns a `reviewed` item that has a checkout, leaving it `reviewed`; the item carries `accepted_review_id`/`accepted_by`/`accepted_at`, `submitted_review_count` and (`reviews:manage` only) `draft_authors`, which shares `reviewAuthorsSql` with `DELETE /intake/{id}`'s authors; `overdue` is any checkout past 14 days; `GET /intake?awaiting_acceptance=true`.
- BS#2803: `POST /intake/{id}/file` (`reviews:manage` AND `catalog:write`) files a `reviewed` item (an accepted review; a citation does not stand in, and `mayFileItem` in `intake.service.ts` is the one check, shared with the gate's `intake` basis) in one transaction, as `new_release` (`planLibraryFiling` before the item lock, `fileLibraryRelease(input, { kind: 'intake', intakeItemId: id }, tx)` after it, `completeLibraryFiling` after the commit) or `existing_release` (the library row `FOR KEY SHARE` first, which is the existence check: a missing release is 400), stamping `album_id` on every review (drafts too) and print of the item, keeping the accept columns, clearing the holder and request, deleting the passes; 409 `not_reviewed` / `state_changed`.
- BS#2804: `POST /intake/{id}/print` (`reviews:manage`) prints the item's accepted review (`accepted_review_id`) from any state that has one (`reviewed`, `filed`, `finalized`); no accepted review, or a handwritten one, is 409 `not_reviewed`, and it never answers `state_changed`.
- One transaction (`printIntakeItem`, `services/review-print.service.ts`), locking through `lockRecordSubject(tx, { intake_item_id }, 'update')`: a filed item's library row `FOR KEY SHARE`, then the item `FOR UPDATE`, then the accepted review `FOR UPDATE`; an unfiled item takes no library lock. An `undefined` answer wrote nothing and runs the transaction once more; a second `undefined` is 404.
- Print appends a `review_prints` row (item, its release or null, review, current revision, caller) and stamps the item's `printed_by`/`printed_at` (the latest print) through the exported `printSlip`, which the release print reuses; `writeFirstRevisionIfMissing` (`reviews.service.ts`, also used by `updateReview`) first writes revision 1 for a submitted review with no history. The `IntakeSlip` text is the printed revision's; `fcc_notes` is the record's confirmed FCC notes (BS#2863, below). Printing locks nothing: the author's later PATCH succeeds.
- BS#2804: `POST /intake/{id}/finalize` (`catalog:write` alone) moves `filed` to `finalized`, stamping `finalized_by`/`finalized_at`; any other state is 409 `state_changed`. 409 `in_rotation` while a `rotation` row with the item's `album_id` is active by `rotationActiveSql()` (never `intake_items.rotation_id` alone, which `SET NULL`s when the dedup job deletes a loser's row and is never set by `existing_release`); the message names the latest kill date or says none is set. The response omits the manager-only `passes` and `draft_authors`.
- BS#2798: six `POST /intake/:id/<action>` transitions (checkout, release, request, cancel-request, accept, pass), each one `UPDATE … WHERE <effective-state precondition> [AND identity] RETURNING` — 409 `state_changed` when no row matches, a follow-up read (`refusalFor`) picks 403 vs 409 vs 404.

## `/reviews`

- In-app DJ reviews (BS#2802, slice 10a of BS#2791): `POST /reviews` creates the caller's own `typed` draft about one subject — an intake item they hold (effective state `checked_out` or `reviewed`, `checked_out_by` = caller, read `FOR UPDATE` inside the insert's transaction; else 409 `subject_not_held`) or an existing library release (read `FOR KEY SHARE` inside the same transaction, so a concurrent `DELETE /library/{id}` either waits and sees the review or has already removed the row, which is 409 `subject_not_held`, never a foreign-key 500; BS#2969) — and answers 200.
- `author` is a snapshot of the account's staff name (`readStaffName` in `shared/database/src/staff-name.ts`, BS#3051: `auth_user.real_name`, else `auth_user.name` when it is null, empty or only whitespace) cut to its first 128 code points. That helper is the only file besides provisioning that reads `real_name` for these surfaces; the review, intake, FCC and notice services call it and stay off the lint allow-list (they are the `STAFF_NAME_CALLERS`). `edited_by`, `fcc_notes.reported_by`, `fcc_notes.confirmed_by` and the names in the "your review was edited", "recorded in your name" and "FCC line changed" notices come from the same call. An on-behalf review's `author` is still the text the music director typed.
- `PATCH /reviews/{id}` enforces the editing rules in `services/reviews.service.ts` `editOutcome` (the author at any time, with no print lock; `reviews:manage` always; `publish_*` and `credit` only by the author account, else 403 even for a music director; 400 when a patch would null a submitted `typed` review's text).
- Every edit of a submitted review that changes one of the five content fields appends a `review_revisions` row through the exported `writeReviewRevision` (which takes the review `FOR UPDATE` itself; a submitted review with no history first gets revision 1); a draft or consent-only edit writes none.
- Locking goes through `lockReviewAfterItem` (item first, then the review, plain `FOR UPDATE`), and the PATCH response is read back through `selectReview` after the writes.
- A draft is visible only to its author and whoever recorded it, so anyone else gets a 404 even with `manage`.
- Role-gated `reviews:write` (dj+).
- `POST /reviews/{id}/submit` (BS#2854): `draft` → `submitted`, stamps `submitted_at` and writes revision 1 through `writeReviewRevision` in the same transaction (item `FOR SHARE`, review `FOR UPDATE`, nothing else against `intake_items`); it never moves the intake item, in any state; a second submit is 409 `not_draft`, a `typed` review with no text a 400, and the response is read through `selectReview` after both writes.
- `DELETE /reviews/{id}` answers 204: the author or `reviews:manage`; a review is **in use** when any item's `accepted_review_id` names it or it is the newest `review_prints` row of an item (or of a release with no item), and an author without manage is refused 409 `in_use`; `reviews:manage` is refused 409 `accepted_review` when any accepting item is `filed`/`finalized` (cited or not, epic decision 40), otherwise one `UPDATE … WHERE accepted_review_id = $review` (the exported `RELEASE_ACCEPTED_REVIEW` `SET`, reused by BS#2860) returns every unfiled accepting item to its holder or the pile and clears the three accept columns before the delete.
- Delete locks through `lockReviewAfterItem(tx, id, 'update', { acceptingItems: true })`: the review's own item and every accepting item in one `FOR UPDATE` statement, ascending by id, before the review, and the accepting items are read again `FOR UPDATE` (ascending by id) for the refusal.
- `DELETE /intake/{id}` fills `deleted_review_authors` through `reviewAuthorsSql` (shared with BS#2860's `draft_authors`).
- Reads (BS#2805, `reviews:read`, never lock, never write): `GET /reviews/{id}` and `GET /reviews` (filters `album_id`, `intake_item_id`, `mine`, ANDed, parsed by `parseInt4QueryParam`; unpaginated) apply `reviewVisibleTo` (a draft only to its author and whoever recorded it, MDs included) and answer every `Review` with computed `in_use` (an item accepts it, OR the exported `latestPrintOfCopy` fragment, the same one `deleteReview`'s print half runs), `on_cover`, `printed_revision_id`, `printed_at`, `revision_count` (BS#2861, a count of `review_revisions` through `reviewRef`; 0 until a review's first edit if it predates edit history), as correlated subqueries of one statement.
- BS#2865: `POST /library/{id}/print` (`reviews:manage` alone; nothing in the catalog changes) prints a typed, submitted review that is in the release's list, for a release that may have no intake item. `printReleaseReview` (`services/review-print.service.ts`, beside `printSlip`) locks the release through `lockReleaseRow` (`FOR KEY SHARE`, a `false` is the 404), then the review `FOR UPDATE` selected through `reviewInReleaseList` (the membership rule of `GET /reviews?album_id=`, exported from `services/reviews.service.ts`); a missing, draft, handwritten or other-release review is one 400. It appends a `review_prints` row with `intake_item_id` NULL through `printSlip`; nothing on `intake_items` is written or locked, and the membership check reads it unlocked. The slip's artist is the release's displayed one (`coalesce(nullif(library.alternate_artist_name, ''), artists.artist_name)`, the `alternate_artist_name || artist_name` rule filing hands to enrichment), so a compilation under a V/A bucket names its own artist. The latest such row is what makes the review `in_use` and `on_cover` in the release's list. Printing a copy's slip stays `POST /intake/{id}/print`.
- `GET /reviews/{id}/revisions` (BS#2861, `reviews:read`) returns the review's `ReviewRevision`s newest first, a bare array, behind the same `reviewVisibleTo` (404 for a draft the caller may not see, `[]` for one they can); `edited_by` is Mixed PII, returned only there.
- `on_cover` is `false` everywhere except the `album_id` list, which selects it once as an alias and sorts by that alias first (then `coalesce(submitted_at, last_modified)` desc, `id` desc); that list is `reviews.album_id` = the release plus the reviews of the release a filed/finalized item of it cites.
- BS#2866: `POST /reviews` with `author`/`author_user_id`/`medium`/`accept` (`reviews:manage`, else 403) is `recordReview`: free-text `author` (required, kept whole, 400 over 128 code points), a linked `author_user_id` (unknown is 400) who is then the author, `medium` `typed` or `handwritten` (no text needed), no surface ticked and `credit` null (sending either is 400), the subject in any state with no hold rule.
- `accept` (default true, `intake_item_id` subjects only) creates the review `submitted` and accepted in one transaction through `writeSubmission` and `writeAcceptance`, the same writes submit and accept use; a typed review then needs text.
- A review of a `filed`/`finalized` item carries its `album_id`; locks are the library row `FOR KEY SHARE`, then the item (`FOR UPDATE` with accept, `FOR SHARE` without).
- BS#3058: `GET /reviews/reviewers` (`reviews:manage`, registered before `/:id`) lists the non-banned accounts whose membership roles pass `canWriteReviews` (`utils/review-grants.ts`), the same test as `/intake`'s `dj_id` 400. `name` is `staffNameSql` (real name, else account name; never `dj_name`), sorted case-insensitively; it goes in the body only, never a log or tag.

## `/fcc-notes`

- `POST /fcc-notes` (BS#2862, `reviews:write`): exactly one of `album_id` and `intake_item_id` (parsed by `parseRecordSubject`, a 400 for both, neither or an id that is not a positive int4), plus `track` and `note`, each non-blank after trimming and with no length bound; answers 200 with the `FccNote`.
- No hold rule: any DJ reports against any logged record in any state and against any library release. A subject that names no release or item is a 400, not a 409.
- The note is created `reported`, `reported_by` a `readStaffName` snapshot of the caller (their real name, else `auth_user.name`; see `/reviews`) and `reported_by_user_id` the caller; a caller with no account row to snapshot is a 403 and nothing is written (migration 0187 makes `fcc_notes.reported_by` NOT NULL).
- Locks go through `lockRecordSubject(tx, subject, 'share')`: the library row `FOR KEY SHARE` first (a missing release is the 400), then the item `FOR SHARE`. An item the lock does not find may have been filed between the unlocked read and the lock, so the transaction runs once more, and a second miss is the 400; the note is never written with a NULL `album_id` for a filed item.
- A note of a `filed` or `finalized` item is stamped with the item's `album_id` at creation, and `POST /intake/{id}/file` stamps `album_id` on every note of the item in its own transaction (both arms, no status filter). A note keeps its `intake_item_id` after the stamp.
- The service returns `notice` (the note, the record's artist and album, the reporter's user id) from inside the transaction, and the controller starts `void notifyFccNoteReported(notice)` after the response (BS#2863): one email to every music director through `notifyMusicDirectors({ subject, lines, links: [{ path, label }], context })`, not awaited, a failed send logged and swallowed. A report by a caller holding `reviews: manage` sends none (decided in the controller from `reviewsActor(req).manage`). The copy is the station's, decided 2026-10-06 and pinned in `tests/unit/services/review-notices.service.test.ts`: subject `FCC note to confirm: {artist} – {album}`, the reporter's line, the `{track}: {note}` line, and a link to `/dashboard/admin/intake` labelled `Open FCC notes to confirm`.
- `GET /fcc-notes` (`reviews:read`): a record's list takes exactly one of `album_id` and `intake_item_id` (`parseInt4QueryParam`, a 400 for both or a malformed value), both statuses unless `status` is sent, oldest first (`reported_at`, then `id`), a bare array. `?album_id=` includes the notes stamped at filing. With neither id, only `status=reported` is answered (the waiting-list bullet below); anything else without a subject is a 400.
- Every `FccNote` response is the exported `selectFccNotes`: one select with left joins, `artist_name` and `album_title` read at response time from the release (and its artist) when the note has an `album_id`, else from the intake item; nothing is stored.
- `POST /fcc-notes/{id}/confirm` (BS#2863, `reviews:manage`): one `UPDATE … WHERE id = ? AND status = 'reported' RETURNING`, stamping `confirmed_by` (a `readStaffName` snapshot of the caller, their real name else `auth_user.name`; a caller with no account row to snapshot is a 403 and nothing is written) and `confirmed_at`, then answers the `FccNote`: the row the UPDATE returned, with the record's artist and album read in the same transaction after it (the UPDATE holds the note's row lock until commit, so a delete cannot land between). A note already `confirmed` is answered 200 unchanged, the first confirmer's stamp kept; no such note is 404; a malformed id is 400 (`parseInt4PathId`).
- `DELETE /fcc-notes/{id}` (BS#2863, `reviews:write`): a caller with `reviews:manage` deletes any note; anyone else only a note they reported (`reported_by_user_id`) while it is `reported`. Those conditions are in the `DELETE`'s `WHERE`, not a prior read, so a reporter's delete racing a confirm either removes a reported note or matches nothing; one follow-up read turns zero rows into 404 or 403. 204, no body. A removed note is deleted, not a third status.
- Neither reads an intake item or a review: each is one statement on the note's own row, so the item-then-review lock order is not involved. `tests/integration/fcc-notes-delete-confirm-race.spec.js` holds the row lock on one connection to force each order of a delete and a confirm.
- `GET /fcc-notes?status=reported` with no subject (BS#2863, the music directors' waiting list): every unconfirmed note at the station, oldest first (`reported_at`, then `id`), unpaginated, through the same `selectFccNotes`. The route gate stays `reviews:read`; the controller checks `holdsReviewsManage` for this form and answers 403 without it. `status=confirmed` with no subject, no subject without a status, and an unknown `status` are 400 for every caller; `status` with a subject keeps only that status.
- The slip's `fcc_notes` (BS#2863) is `confirmedFccNotesOf(tx, target)` called by `printSlip`: the confirmed notes whose `intake_item_id` is the target's item, or whose `album_id` is the target's release (each when non-null), as `{ track, note }`, oldest first. It is read after the print-log row inside the print's transaction, takes no lock, and a target with neither id reads nothing. A note confirmed after a print is a reason to reprint; the print log does not track notes.

## Review notices to authors and music directors (BS#2864)

- Three emails, no in-app inbox; every send starts after the commit, is not awaited (`void …` in `reviews.controller.ts`), and a failure is logged, reported and swallowed, so the response is unchanged. The copy is the station's (2026-10-06) and is pinned in `tests/unit/services/review-notices.service.test.ts`.
- **Notice 1** (`notifyReviewEdited`, to the review's linked account): `PATCH /reviews/{id}` by someone other than `author_user_id` that wrote a revision of a submitted review. A draft, a consent-only patch, an unchanged patch, the author's own edit and a review with no linked account send none.
- **Notice 2** (`notifyReviewRecorded`): an on-behalf `POST /reviews` that carries `author_user_id`, draft or accepted, unless that account is the recorder's own.
- **Notice 3** (`notifyFccChanged`, to every music director except the one who made the edit, excluded by account id (`excludeUserIds` on `notifyMusicDirectors`, decided 2026-10-07); when the editor is the only music director, nobody is emailed): an edit of a submitted review whose `fcc` differs from the stored one, on a review that has been printed (`printed_at` is set; an unprinted review costs no read) and is the latest print of at least one copy (`latestPrintOfCopy`, evaluated on the locked review inside the PATCH transaction). It lists a copy only when the new line differs from the `fcc` of that copy's latest print's revision (`review_prints.revision_id`, the one the slip carried), not from the previous revision: a line edited away and back leaves a sleeve that still shows it, and an edit that matches one copy's slip lists only the others. A print whose revision is gone is of unknown content and is listed. One link each: an intake item links to `/dashboard/admin/intake/{id}` (a print row with an `intake_item_id` is that item's copy even when it also carries the filed release's id), a release with no item to `/dashboard/album/{id}`. An edit by a music director of someone else's printed review that changes `fcc` sends notices 1 and 3.
- Notices 1 and 2 go through `notifyAccount`, which reads that account's `auth_user.email` and skips a missing account, an account with no `member` row (a former station member gets neither notice) and one whose ban is in force (`isBanInForce`). The names they carry (the editor in notice 1, the recorder in notice 2) are the snapshotted staff names from `readStaffName`: the real name, else `auth_user.name` (BS#3051). The "review waiting" holder name (`readReviewNotice`, `staffNameSql`) and the "request passed" DJ name (`notifyPass`, `readStaffName`) are the same (BS#3052); a failed lookup in `notifyPass` sends the notice without a name.
