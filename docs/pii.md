# PII field registry

The DJ-name family of columns spans two genuinely different kinds of data — a public on-air handle, and a legally-collected legal name — that have historically lived close enough together in the schema and the code to get confused with expensive consequences. This registry is the single place that states, per column, which kind it is, why it exists, where it's allowed to be read, and what (if anything) stops a new read site from leaking it. When adding a new column or read site anywhere near `real_name`/`dj_name`/`name`, check this table first.

## DJ name vs real name: a short history

Before commit `a0cd1979` (2025-12-31), the on-air handle and the legal name lived on two separate columns of the old `djs` table: `dj_name` (handle) and `real_name` (PII). That commit collapsed the table into `auth_user` and introduced `djName || name` fallback chains in the resolution code, while dj-site's admin provisioning flow began filling better-auth's required `name` field with `realName || username`. From that point on, `auth_user.name` — better-auth's innocuously-named, required display column — silently became a second, unmaintained copy of the legal name, and any ordinary `.name` read on a DJ row was a latent PII leak to a public surface: the flowsheet, the tubafrenzy mirror, wxyc.info. Several incidents (BS#1286, BS#1288, `2a37bbc6`, BS#1393, BS#2281) trace back to that one structural fact. `auth_user.name` has been converted back into a public-safe display value — the on-air handle if the DJ has one, else their username: the `databaseHooks.user` derivation hooks enforce it on every write, and the one-shot backfill (`jobs/auth-user-name-backfill`) rewrote the pre-existing rows in production on 2026-08-28 (139 of 144 non-anonymous rows rewritten; the 2 rows whose only legal-name copy lived in `name` were preserved into `real_name` first, per the plan's Track 2a). This registry, the `COMMENT ON COLUMN` annotations in migration `0157_dj-name-pii-column-comments.sql`, and the `wxyc/restricted-real-name` ESLint rule exist to keep the two kinds of name from re-conflating.

## Enforcement

<!-- @rule id=real-name-restricted-lint enforced-by=eslint-rules/restricted-real-name.cjs added=2026-08-27 -->

**Reading `realName`/`real_name` outside an allow-listed file is a lint error.** Enforced by the `wxyc/restricted-real-name` ESLint rule (`eslint-rules/restricted-real-name.cjs`, registered in `eslint.config.mjs`, scoped to `apps/**/*.ts`, `shared/**/*.ts`, `jobs/**/*.ts`). Full rationale — the incident this closes, why both AST shapes are matched, why there's deliberately no `user.name` clause, the allow-list, and documented known gaps — lives in the rule's own docblock.

`shared/database/src/staff-name.ts` is on the `ALLOW_LIST` (BS#3051, exact path) because the station decided that staff-only screens show people by real name. Its `readStaffName` is the single read that stamps `reviews.author`, `review_revisions.edited_by`, `fcc_notes.reported_by` and `fcc_notes.confirmed_by`, and `staffNameSql` is the matching fragment for joins and the computed intake names (BS#3052); both fall back to `auth_user.name` when `real_name` is null, empty or only whitespace (space, tab, line breaks, non-breaking space). The review, intake, FCC and notice services call the helper and are deliberately **not** on the list, so a new `real_name` read in any of them is still a lint error, and `shared/database/src/dj-name.ts` stays off it too. Because a caller of the helper never writes a `realName` access, the same rule separately restricts the helpers themselves: importing, re-exporting or member-accessing `readStaffName` or `staffNameSql` is a lint error outside `STAFF_NAME_CALLERS` in `eslint-rules/restricted-real-name.cjs` (exact paths: `apps/backend/services/reviews.service.ts`, `apps/backend/services/fcc-notes.service.ts`, `apps/backend/services/intake.service.ts` and `apps/backend/services/review-notices.service.ts`), so a new caller is an allow-list edit in the same PR. The rule does not inspect `export *`, which is how the `@wxyc/database` barrel exposes them. Nothing the helper returns may reach a public surface.

`apps/auth/station-signup.ts` is on the `ALLOW_LIST` (BS#2360) ahead of the file itself being written: the station signup endpoint (BS#2361, blocked by this issue and BS#2359) will construct `provisionUser({ realName, ... })`, an object-literal property key — an `ObjectExpression`, the exact shape the rule flags (destructuring `const { realName } = ...` is not; see the rule's Known Gap #1) — and the plan splits the groundwork out from the endpoint PR so the endpoint lands lint-clean on arrival.

**A failed query's bound parameters never reach Sentry or the logs (BS#3054):** log a caught database error on a name-writing path through `redactQueryParams`. Helper: `redactQueryParams` in `shared/observability/src/redact-query-params.ts`; call-site list, what is not scrubbed and the known limits: the subsection below. Also enforced by `tests/unit/observability/console-redaction.test.ts` and `tests/unit/auth/auth-log-redaction.test.ts`.

### Failed-query parameters: how the redaction works and what it leaves

drizzle-orm's `DrizzleQueryError` message is `Failed query: <sql>\nparams: <params>`, so every bound value (since BS#3051 a legal name: `auth_user.real_name` and the four `readStaffName` stamp columns) is in the message, the stack and the `params` property, and the postgres.js `cause` carries them again in `parameters`/`args`. The redaction is structural (everything from the first `\nparams: ` on), builds a plain copy that cannot throw on postgres.js's non-configurable properties, and falls back to a minimal error (class name and redacted message, no stack, so the event is never grouped under the helper's own frames) or `[unloggable error]` rather than throw on the error path. Two guards fail closed: a stack that still holds an unredacted params line after the message swap (a message shortened after V8 formatted the stack) is cut at that line, and the rebuild stops at the depth `redactError` copies (`MAX_DEPTH`) and withholds the stack of any link that still holds one, so a `linkedErrorsIntegration` `limit` above 8 cannot send an unredacted query error. Sentry parses `error.stack` into `exception.values[].stacktrace` before `beforeSend` runs, and a params line becomes frames carrying the bound values (a bound timestamp even gives them a line number), so no frame filter can be trusted: `beforeSend` rebuilds each exception value's message and stacktrace from `hint.originalException` redacted by `redactQueryParams`, with the client's own stack parser, matching the cause chain by position. With no original exception, or a value it cannot match, the value is scrubbed in place and its stacktrace is dropped when the message held a params part; a last pass scrubs every string in the event. better-auth is covered twice: its `logger.log` sink fails closed until the auth app registers the redactor, and the auth process wraps `console.error`/`console.warn`, because better-call's router prints the raw error outside the logger and the only setting that stops it (`onAPIError: { throw: true }`) changes the client's response.

Call sites that route a caught database error on a name-writing path through `redactQueryParams`: backend `errorHandler` (unhandled branch); auth `app.ts` `[PROVISION USER]`, `[UPDATE IDENTITY]`, `[STATION SIGNUP]`, `[COMPLETE ONBOARDING]`; auth `create-default-user.ts`. Sentry: backend and auth `instrument.ts` (`beforeSend`, `beforeBreadcrumb`). better-auth's own logs: `authLogHandler` and the auth process's console wrapper. Not scrubbed because they bind only ids and roles: the `[PROVISION USER]` cleanup delete, the other `auth.definition.ts` hook logs, and `fallbackErrorHandler`'s non-production response body. A new route or job that catches such an error must log it through `redactQueryParams`.

Known limits. None binds a name in today's code, but a change that does must close them first: `AggregateError.errors`, an `Error` held in an own property other than `cause`, and a `cause` that is not an `Error` are not descended into, so an error nested there comes back unredacted (the auth app's one `AggregateError` producer, `bootstrapTrustedClients`, binds OAuth client fields, not names). Sentry's `onUncaughtException` and `onUnhandledRejection` print through the native console inside `consoleSandbox`, which bypasses the auth process's console wrapper (the backend has no wrapper): `onUnhandledRejection` prints `reason.stack`, while `onUncaughtException` runs `logAndExitProcess`, which calls `console.error(error)` and so prints the whole inspected error, including its `params` array. The fail-closed sink used before the auth app registers its redactor withholds an `Error` passed as an argument but passes one inside an object or array, and a cross-realm `Error`, through unchanged. `redactLogValue` does not invoke accessor properties, so an `Error` behind a getter is left as is. It also does not descend into a class instance, `Map` or `Set` passed to `console.error`/`console.warn`, or into an object or array nested more than 3 levels deep, so an `Error` held there is printed as is. An `Error` passed in Sentry `extra` or `contexts` is normalized by Sentry into `{ message, stack, params: [...] }`; the final scrub pass rewrites only strings containing `\nparams: `, so the `params` array goes out unredacted.

Spans are safe only because both `Sentry.init` calls pin `traceLifecycle: 'static'` (a unit test fails if either stops): Sentry 11's Express channel puts `error.message` in the failing layer's span status, static transaction JSON drops that message, and span streaming would send it as an attribute, bound parameters included. Moving the filter to streaming (BS#2959) must scrub span statuses first.

Sentry's stack-frame locals (`stackFrameVariables`) are not a leak path today: in `@sentry/node` 11.4 `localVariablesIntegration` is a default integration but starts its inspector only when the client option `includeLocalVariables` is set, and no `Sentry.init` in this repo sets it. Setting that option on a service that touches staff names would attach locals such as `author`, so it needs a scrub in the same hook first. Not covered: other Postgres constraint-violation details pass through unchanged on the driver error under a `DrizzleQueryError`'s `cause`; the only unique constraint on these tables is `review_revisions (review_id, revision)` and the foreign keys report ids (`Key (album_id)=(...)`), so none carries a name. The log line is the only place such a detail surfaces. Postgres server messages that quote a value (`invalid input syntax for type ...: "<value>"`, `invalid input value for enum ...`) on the cause's message are not redacted: they need a name bound to a non-text column, and every column written with a name here (`auth_user.real_name`, `reviews.author`, `review_revisions.edited_by`, `fcc_notes.reported_by`/`confirmed_by`) is text, so no such message can quote one.
