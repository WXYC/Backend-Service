### `@wxyc/flowsheet-etl`

Path: `jobs/flowsheet-etl/`

**One-shot (retained, unscheduled).** Flowsheet ETL: sync `shows` + `flowsheet` from tubafrenzy. Was `*/30`; Phase 3 of the tubafrenzy decommission ([WXYC/wiki#88](https://github.com/WXYC/wiki/issues/88)) flipped both tables to Backend-canonical and set `job-type: one-shot`, so the deploy no longer registers a crontab entry. **Refuses to run unless `LEGACY_ETL_ALLOW_BACKWARDS_WRITE=1`**: its upserts key on `legacy_show_id`/`legacy_entry_id`, which the live mirror back-stamps onto dj-site-originated rows, so an import overwrites Backend-canonical data with tubafrenzy's mirror copy (`backwards-write-guard.ts` has the full mechanics). Its `cronjob_runs` watermark froze when the cron stopped — bound it before any manual run. Kept invocable for the Phase 6a maintenance window; its `album_id` linkage-repair tail pass now lives in `@wxyc/legacy-linkage-resolve`.

### `@wxyc/rotation-etl`

Path: `jobs/rotation-etl/`

**One-shot (retained, unscheduled).** Rotation ETL: sync `rotation` from tubafrenzy. Same Phase 3 flip and same `LEGACY_ETL_ALLOW_BACKWARDS_WRITE=1` gate as the flowsheet sibling, but a **different hazard** — there is no rotation mirror, so `legacy_rotation_id` is never back-stamped onto a dj-site row and this job cannot reach one. What it does reach is every row that ever came from tubafrenzy, whose `rotation_bin`/`kill_date`/`album_id` and denormalized display columns it reverts, and whose `discogs_release_id_source` it can restamp to `tubafrenzy_paste` (BS#1029). Frozen watermark applies here too. Its `album_id` linkage-repair tail pass now lives in `@wxyc/legacy-linkage-resolve`.

### `@wxyc/library-etl`

Path: `jobs/library-etl/`

**One-shot (retained, unscheduled).** Library ETL: sync `library` + crossreferences from tubafrenzy. Same `LEGACY_ETL_ALLOW_BACKWARDS_WRITE=1` gate as its flowsheet/rotation siblings (BS#2581). ### `@wxyc/legacy-linkage-resolve`

Path: `jobs/legacy-linkage-resolve/`

Recurring cron (`*/30 * * * *`, WXYC/wiki#88 Phase 3): links `flowsheet.album_id` and `rotation.album_id` to the `library` row once it exists. The flowsheet webhook resolves `album_id` exactly once at write time — a race against the librarian, who routinely files the release after the MD bins it — and never refreshes it, so a row whose library row lands second stays unlinked forever. This is the `resolveAlbumIds` tail pass lifted verbatim out of `flowsheet-etl` + `rotation-etl` when Phase 3 unscheduled them: the one half of those jobs that was never a backwards write (it reads and writes only Backend's own tables, never tubafrenzy). Pure SQL, DB-only, no `@wxyc/lml-client`, exempt from the LML cron-spacing policy. Anti-joined on `album_id IS NULL` so an idle run is a no-op; `ANALYZE` after any pass that wrote; `--dry-run` reports candidate counts. A third, text-match pass (BS#3061) re-applies `wxyc_schema.text_match_key()` to plays logged before their library row existed, stamping `direct_text_match` / `1.0`; it is bounded by a recent-`add_time` window that is a cost bound, not a watermark, and **ships disabled** — it writes nothing unless `LINKAGE_RESOLVE_TEXT_MATCH_WINDOW_DAYS` is a positive integer (enabling is the manual step tracked in BS#3063; `--dry-run` always reports its would-link count over that window, else 90 days) and shares the drain check and both stand-downs. The first two passes have no watermark: no watermark (set-based over the current NULL cohort) and no cooperative pause (deferring the repair through a long show is worse than the contention it avoids). **Liveness (BS#2064, hardened BS#2071, extended BS#2413 and BS#2594)** — because a healthy idle run is indistinguishable from a stopped cron, the run carries four signals, the fourth in two kinds: a `Sentry.withMonitor` check-in (the fleet's first; missed check-in ⇒ alert ~10 min after the missed slot, ~40 min after the last successful run), a `cronjob_runs` heartbeat read back next run to warn on a gap past `LINKAGE_RESOLVE_MAX_GAP_HOURS` (4 h), and a per-pass drain check that measures its cohort count and its UPDATE inside one data-modifying CTE — one statement, one Postgres snapshot — and warns when `resolved` falls short of `candidates`; and two stand-down kinds, each **withholding the heartbeat** so repeated collisions escalate via the gap warning: a lock-contention stand-down (BS#2413) — an empty cohort issues no UPDATE, and a pass with work gives up its slot in 750 ms (`lock_timeout`, `55P03`) instead of waiting out a long `library-etl` transaction — and a retired-linkage-candidate stand-down (BS#2594) — a librarian's `DELETE /library/:id` racing this job's own UPDATE past the FK insert-check surfaces as a `23503` on `flowsheet_album_id_library_id_fk` / `rotation_album_id_library_id_fk` (`isRetiredLinkageCandidateError`, `jobs/legacy-linkage-resolve/retired-candidate.ts`), converted to a clean stand-down rather than a failed run. Each fires its own fingerprint — `legacy-linkage-resolve.lock_contention` vs. `legacy-linkage-resolve.retired_linkage_candidate` — so the two are distinguishable in logs and Sentry. Two earlier shapes got that comparison wrong: the original BS#2064 shape (separate pre-UPDATE COUNT vs. `resolved`) false-positived on a row leaving the cohort between the two statements — a concurrent `broken-fk-recovery` run, a hand-run `flowsheet-etl`/`rotation-etl` repair pass (unscheduled but still invocable, gated behind `LEGACY_ETL_ALLOW_BACKWARDS_WRITE=1` — three concurrent repairers, not one, though two of the three require that env var deliberately set), or a deleted/edited candidate row; a first BS#2071 attempt (separate pre-UPDATE COUNT vs. a post-write re-COUNT) traded that for the more common false positive of a row _entering_ the cohort in the same gap, since `library-etl` then shared this job's exact `*/30` slot (unscheduled in WXYC/wiki#89 Phase 3.5, so that particular collision is now historical — the job stays invocable by hand, which is why the stand-down remains). Folding both counts into one statement closes both of those gaps, but does not make `resolved === candidates` guaranteed: a row already in `cohort` can still be concurrently UPDATEd or DELETEd while the statement runs, and Postgres's EvalPlanQual re-check can drop it out of the UPDATE (the same mechanism findings 1/2 fixed by restoring `album_id IS NULL` to the UPDATE's own WHERE, not just the candidate SELECT) — a shortfall is evidence worth a warning, never proof of a stuck UPDATE. The heartbeat row is a **liveness signal only — never a delta bound**: a `last_run` filter on either cohort would permanently strand the rows this job exists to repair — `tests/unit/jobs/legacy-linkage-resolve/job.test.ts` pins each statement against an exact-match allowlist so any added predicate fails the test. Recipe generalized in `docs/ops-cron-scheduling.md`.

### `@wxyc/streaming-url-remediation`

Path: `jobs/streaming-url-remediation/`

One-shot host remediation (BS#1715): scan `album_metadata` + `flowsheet` for rows whose stored `spotify_url` is not a Spotify host (or `apple_music_url` is not an Apple host) — the pre-guard pollution BS#1710 established — and rewrite each row through the pure `computeStreamingUrlFix` arbiter (`@wxyc/lml-client` `isSpotifyUrl`/`isAppleMusicUrl`) so every column holds only a host-correct value: relocate a real link that landed in the wrong slot, null an unrecoverable foreign value so the read path synthesizes the `open.spotify.com/search/…` fallback. **No LML** — unlike the BS#1672 `streaming-url-upgrade` sibling (structural donor; re-queries LML to upgrade _search-shaped_ URLs), the correct value is already in the row or nowhere, so the fix is pure local host arbitration. ### `@wxyc/flowsheet-show-split`

Path: `jobs/flowsheet-show-split/`

One-shot repair (WXYC/dj-site#1035): split a show that accumulated several DJs' sets into one show per DJ, promoting the `dj_join` / `dj_leave` boundary markers to `show_start` / `show_end`. `POST /flowsheet/join` routes start-vs-join on `current_show?.end_time !== null`, so a DJ who leaves without signing off collects every later go-live as a silent guest join — BS#1861 closed only the variant where the sign-off DID happen and `end_time` lagged, since both of its guards key on a `show_end` marker existing. Boundary rules are pure and unit-tested (`segment.ts`) against production show 1951224's real 2026-08-28 sequence: a `dj_join` is a handoff unless it closes within `--min-segment-seconds` (default 120) — the blind-toggle retry signature, which would otherwise mint a four-second show; a segment ends at its OWN `dj_leave` when one exists, since ending it at the next go-live would invent airtime — but only when that leave falls inside its own segment's play-order run, since `findMatchingLeave` matches by `dj_name` across the whole show and a co-host who signed off inside the NEXT DJ's set would otherwise have their `show_end` filed among that show's entries, leaving two shows overlapping. **Re-pointing `show_id` is not the whole repair:** `flowsheet.dj_name` is denormalized once per request by `POST /flowsheet` (`resolveDjNameForShow`), so every later DJ's tracks carry the ORIGINAL DJ's handle — and that column, not the show join, is what the v2 projection, `/playlists` and the search service's `DJ_NAME_EXPR` read, so the job re-denormalizes it per segment (skipping `dj_join`/`dj_leave`, which name a person, not a show; `flowsheet-dj-name-backfill` cannot help — it selects `dj_name IS NULL` and these are non-null and wrong). Marker promotion likewise rewrites `flowsheet.message`, since `createJoinNotification` writes `"<name> joined the set!"` where `startShow` writes `"Start of Show: <name> joined the set at <time>"` and `message` is on the public read path (`markers.ts` reproduces both live writers verbatim). New shows are written `legacy_show_id = NULL` on purpose, keeping them outside `flowsheet-etl`'s `ON CONFLICT (legacy_show_id) DO UPDATE`. **The tubafrenzy half is not optional:** that upsert sets `end_time: excluded.end_time` whenever it differs and `epochMsToDate(0)` is `null`, so while tubafrenzy holds `SIGNOFF_TIME = 0` an ETL pass reverts the repaired `end_time` to NULL — the job stamps `FLOWSHEET_RADIO_SHOW_PROD.SIGNOFF_TIME` to the same instant to make that upsert a no-op instead (`flowsheet-etl` is unscheduled today, so this is latent, not active). Deliberately does NOT re-point tubafrenzy's `FLOWSHEET_ENTRY_PROD.RADIO_SHOW_ID` — `GLOBAL_ORDER_ID = RADIO_SHOW_ID * 1000 + SEQUENCE_WITHIN_SHOW` would need recomputing per row plus a Tomcat restart to clear `FlowsheetEntryCache`; tubafrenzy's copy stays one long show while Backend (what iOS, dj-site and the archive read) carries the corrected shape. **Not re-runnable** — a second pass sees its own promoted `show_start` markers where the boundaries were — hence one transaction and no `DB_SYNCHRONOUS_COMMIT=off`. Requires `--show-id`, no default; `--dry-run` logs the full plan.

### `@wxyc/station-signup-review`

Path: `jobs/station-signup-review/`

Daily cron (BS#2364, station-signup-review plan): while any self-signed-up account is pending manager review (`auth_user.self_signup_at IS NOT NULL AND self_signup_reviewed_at IS NULL`), emails a digest to `STATION_SIGNUP_ALERT_EMAIL` naming every pending account, its days-pending, and this run's per-account downgrade decision. No watermark — unlike `metadata-no-match-digest`, this is a point-in-time snapshot re-sent daily for as long as anything is pending, not a since-last-run feed. **The only automatic privilege downgrade in the fleet**, so the run is plan → notify → apply: it decides per account without writing, sends the digest naming the accounts downgrading today, then writes — and deliberately does NOT gate the write on the send succeeding, since gating the backstop on SES health would mean an unset `SES_FROM_EMAIL` silently downgrades nobody, forever, while the digest is level-triggered and a failed send costs one day of awareness. An account pending `DOWNGRADE_AFTER_DAYS` (30 — chosen to exceed any holiday break, so it never fires mid-break and strands a working DJ) or more has its `auth_member.role` written directly from `'dj'` to `'member'`, guarded `WHERE role = 'dj'`. Three guards, all failing toward "wait a few minutes": the `STATION_SIGNUP_DOWNGRADE_ENABLED` kill switch (strict `=== 'true'`, **defaults OFF**, re-read every run because cron is `docker run --env-file .env`); an on-air skip for any account holding an open show (`shows.end_time IS NULL AND (primary_dj_id = userId OR EXISTS (show_djs …))`, served by `shows_open_start_time_idx`) which also defers when the guard query itself errors, because a DJ demoted mid-show cannot `POST /flowsheet/end` and their abandoned open show swallows every later go-live as a guest join; and `auth_user.self_signup_downgraded_at` (migration 0161), the terminal marker that makes the actuator fire **at most once per account** — without it a downgraded account never left the pending cohort (the downgrade deliberately does not stamp `self_signup_reviewed_at`, which is the manager's queue and dj-site's roster predicate), so every manager re-promotion was undone the next morning, forever. Safe as a direct write only for this role pair, because `grantsAdminFlag` is `normalizeRole(role) === 'stationManager'` — neither `dj` nor `member` touches the `auth_user.role='admin'` flag (see WXYC/Backend-Service#2171 on not making that drift worse). The only `auth_user` column it writes is `self_signup_downgraded_at`, in the same transaction as the role flip; never `auth_user.role`, never deletes, never bans — reversible with one roster edit that now sticks. `tsup` emits `dist/query.cjs` + `dist/downgrade.cjs` so `tests/integration/station-signup-review.spec.js` runs the real predicates against real Postgres.

### `@wxyc/auth-log-prune`

Path: `jobs/auth-log-prune/`

Daily EC2-cron (BS#2363; renamed from `station-signup-attempt-prune` by WXYC/Backend-Service#2535, parent epic #2534; extended to a second table by BS#2536). Two independent single-statement DELETEs under separate try/catch — a failure on one never silently skips the other: `DELETE ... WHERE attempted_at < cutoff` against `station_signup_attempt` via `pruneSignupAttempts` (`shared/authentication/src/station-passcode.ts`, 30-day retention; never touches `station_passcode`), and `DELETE ... WHERE occurred_at < cutoff` against `account_audit_event` via `pruneAccountAuditEvents` (`shared/database/src/account-audit.ts`, `ACCOUNT_AUDIT_RETENTION_DAYS`-day retention, default 730 — the account-modification audit trail's storage substrate, BS#2536; no call sites write to it yet, that's BS#2537). Split from `jobs/station-signup-review` because the failure consequences differ — a failed prune just grows a table, a failed review is a silent manager-review queue and, eventually, a stuck privilege downgrade — so the two want separate alerting. No dry-run, no batching, no paging. Not in the LML slot table (`docs/ops-cron-scheduling.md`'s "Excluded / DB-only" section) — neither prune has a `@wxyc/lml-client` dependency, cannot trip the breaker. Default schedule `27 15 * * *` UTC, ten minutes after `station-signup-review` for readability; no ordering dependency between them.
