# Authentication

The `shared/authentication` workspace package wraps better-auth and provides JWT verification + role-based access control for the API server.

**Key files:**

- `auth.definition.ts` — better-auth config with plugins and hooks
- `auth.roles.ts` — The grant matrix (`WXYC_GRANTS` + `ORG_ADMIN_GRANTS`) and the role construction it feeds
- `auth.middleware.ts` — JWT verification and permission checking
- `auth.client.ts` — Client-side better-auth initialization
- `email.ts` — SES email sending (password reset, verification)

**Roles form a chain** — member < dj < musicDirector < stationManager — but the chain is a **CI-enforced invariant on the grant data, never a runtime mechanism**. `requirePermissions` checks each role's own flat grant set with no fallback to the role below it; the ordering is true because `tests/unit/authentication/auth.roles.test.ts` proves it, not because any code walks it. That distinction is what keeps `flowsheet: ['manage']` meaningful as its own action rather than a proxy for "MD or above".

`@wxyc/shared` owns role _identity and order_ (`ROLES`, `ROLE_ALIASES`, `canonicalizeRole`); this repo owns the **only** grant matrix. Two blocks in `auth.roles.ts`:

- **`WXYC_GRANTS`** — the station domain, typed-total: every role must decide every key (`[]` is an explicit denial), so adding a key to `statement` without deciding it for all four roles is a **compile error**. This replaced the trap where a new key granted to `dj` but left to arrive at `stationManager` via a spread produced a plain DJ with 200 and a station manager with 403.
- **`ORG_ADMIN_GRANTS`** — better-auth's own org-administration keys (`organization`/`member`/`invitation`/`team`/`ac`), held by `stationManager` alone, written out explicitly. It used to be `...adminAc.statements`, which reads as "stationManager gets everything" and is in fact a fixed library-owned set conferring no custom key.

**Permissions per role (station domain):**

| Role           | bin        | catalog    | flowsheet                                     | album_reviews | digital_archive |
| -------------- | ---------- | ---------- | --------------------------------------------- | ------------- | --------------- |
| member         | read/write | read       | read                                          | — (`[]`)      | — (`[]`)        |
| dj             | read/write | read       | read/write                                    | read          | listen          |
| musicDirector  | read/write | read/write | read/write + manage                           | read          | listen          |
| stationManager | read/write | read/write | read/write + manage (plus org administration) | read          | listen          |

`album_reviews: read` gates `GET /album-reviews` (ADR 0011) — the internal surface over the whole DJ form-review archive, without the public `wxycReviews` attach's `social_consent = true` filter, because the form's consent question asked only about social media and internal station tools were never in its scope. The key is deliberately not called `reviews`: ADR 0006 reserves that name for the in-app Review model, a different resource. `member` decides the key as `[]`, an explicit denial rather than an omission; `stripEmpty` drops it before better-auth sees it, so the constructed role is byte-identical to one that never mentioned it.

`digital_archive: listen` gates `GET /digital-archive/albums/:id/playback` (BS#2320) — presigned playback manifests into the auto-DJ Space. Same tier and same `member: []` denial shape as `album_reviews`: the legal boundary is "authenticated DJs", not `catalog: read` (which `member` already holds).

**JWT payload**: `sub` (user ID), `email`, `role` (queried from the organization member table, not `user.role`).

**`requirePermissions` middleware flow:**

1. Extract Bearer token from `Authorization` header via the shared `parseBearerToken` helper — the Bearer scheme is matched case-insensitively per RFC 6750 §2.1 (`bearer`/`Bearer`/`BEARER`), and a bare `Bearer` with no token is rejected with 401. The same helper serves the `AUTH_BYPASS` branch so the two cannot drift (BS#1125).
2. Verify against JWKS endpoint (`BETTER_AUTH_JWKS_URL`)
3. Check issuer and audience claims
4. Resolve the role string through `normalizeRole` → `@wxyc/shared`'s `canonicalizeRole` (403 on `undefined`). This **accepts** more than `WXYCRoles`' literal keys — `admin`/`owner` and case/underscore variants resolve — and **rejects** prototype keys, which the previous `role in WXYCRoles` check let through (`role: 'toString'` resolved and then crashed the middleware with a 500). Stored and emitted role values are always the four station keys; the alias set is read-side only.
5. Check permissions using the role's authorize function
6. 403 if role invalid or permissions insufficient

**Auth bypass**: Set `AUTH_BYPASS=true` to skip JWT verification in tests. Rate limiting is disabled when `NODE_ENV=test`.

**Role mismatch gotcha**: better-auth's organization plugin has built-in roles (`owner`, `admin`, `member`) that overlap with WXYC's custom roles. A `member.role` the alias table can't resolve returns 403 on every request. Organization hooks sync admin-granting roles to `user.role='admin'` for the better-auth admin plugin — via `grantsAdminFlag` (`admin-flag-sync.ts`), which is now the **single** definition of that question. It previously existed as **five** verbatim `['stationManager', 'admin', 'owner']` copies (the grant hook, `hasOtherAdminMembership`'s SQL IN-list, `apps/auth/app.ts`'s boot reconciler `findUsersMissingAdminFlag`, `provision-user.ts`, and a backfill script); the grant path widened with the shared alias table while a hardcoded revocation list would not have, so grant and repair could accept different strings — and the boot reconciler is _specifically_ the retry path for a membership hook that failed, so a narrow copy there meant a membership the hook granted on could never be repaired if the hook died. `hasOtherAdminMembership` therefore filters in TS rather than SQL, and deliberately carries **no `.limit(1)`** — with the role predicate out of SQL, a limit would return one arbitrary membership and a user holding both a `dj` and a `stationManager` row would wrongly lose the flag.

`device-authorization.ts` deliberately does **not** use the alias table: `/device/approve` gates on `Object.hasOwn(WXYCRoles, role)`, so a stray `admin`/`owner` membership row cannot QR-approve a session. That divergence is intentional and commented at the call site.

Prior art: the unmerged `docs/auth-convergence-proposals` branch (2026-02-14) argued that admin is a system axis orthogonal to station roles and that better-auth's built-in org roles should never be _stored_ as WXYC member roles. Both hold here — `admin-flag-sync` implements the first, and nothing in this design stores built-in roles; the alias mapping is read-side normalization for stray or legacy rows only.

**Capabilities (cross-cutting, per-user grants independent of role)**: `auth_user.capabilities` (`text[]`, default `[]`) holds arbitrary capability strings — today `editor`/`webmaster`, granted via `dj-site`'s admin roster page, and `crm_merge` (BS#1884, gating `WXYC/wxyc-crm`'s donor-dedup admin tool). `getAdditionalUserInfoClaim` (`auth.definition.ts`) and the JWT plugin's `definePayload` both emit the array verbatim on the OIDC/JWT `capabilities` claim, with no per-capability-name code change required. There is no dedicated grant endpoint or UI for a capability beyond `editor`/`webmaster` — to grant any capability (including `crm_merge`) to a user, call Better Auth's `admin()` plugin `updateUser` endpoint with `data: { capabilities: [...existingCapabilities, 'crm_merge'] }`, the same call `dj-site`'s `AccountEditForm.tsx` (`updateCapabilities`) already makes in production, run from an authenticated admin session. This is an operator action (a one-off script or `curl` against the admin API), not a `Backend-Service` code path — no schema migration is needed, and `capabilities` is already registered in `additionalFields`. That registration carries `input: false` as of BS#2358, so the array is **not** freely writable: the operator grant path above is unaffected (the `admin()` plugin's `/admin/update-user` hands its `data` object straight to `internalAdapter.updateUser` and never calls `parseUserInput`), but better-auth's public `POST /update-user` can no longer set it. Until that flag landed it could — the route sits behind `sessionMiddleware` only, so any signed-in DJ could grant themselves any capability, `crm_merge` included, and have it emitted on their next JWT/OIDC claim.

**`additionalFields` has two independent gates, `input` and `returned`, and they answer different questions**: `parseUserInput` filters on `input`, so `input: false` stops better-auth's public `POST /update-user` writing a field; `parseUserOutput` filters on `returned`, so `returned: false` stops a field appearing in a response body. A field can be locked against writes and still be emitted on every payload — the two flags are not a pair, and `tests/unit/authentication/pii-additional-fields-input.test.ts` enforces `input: false` as deny-by-default (every field is locked unless it appears in a short, justified `WRITABLE_FIELDS` map) while `returned: false` stays a per-field decision. `returned` is **global, not audience-scoped**: the admin plugin's `/admin/list-users` maps every row through the same `parseUserOutput`, so a field hidden from `/get-session` is also hidden from `dj-site`'s admin roster, and `buildJwtPayload`/`buildOidcUserInfoClaim` spread the whole user object onto the JWT and the OIDC `additional_user_info` claim. Today exactly one field carries the flag: `auth_user.self_signup_reviewed_by` (BS#2358), because it holds _another_ person's `auth_user.id` — the manager who cleared a self-signup review — and without it that id reaches the reviewed DJ and every relying party. The three sibling timestamps `self_signup_at`, `self_signup_reviewed_at` and `self_signup_downgraded_at` deliberately stay returned: `dj-site`'s pending-review predicate is `self_signup_at IS NOT NULL AND self_signup_reviewed_at IS NULL`, read straight off `/admin/list-users`, so hiding either of the first two would silently pin it to a constant — a review queue that never empties, or one that never fills — and hiding the third would leave a manager unable to tell an account `jobs/station-signup-review` auto-downgraded (BS#2364) from one that was always a `member`. None of the three names anyone but the account holder; the downgrade's actor is a cron job, not a person. A "reviewed by ⟨name⟩" display, if it is ever wanted, must come from a `Backend-Service` admin endpoint rather than from re-opening this flag.

**Onboarding completeness is flag-authoritative, not field-derived**: `auth_user.has_completed_onboarding` is the single source of truth for whether a DJ has finished onboarding. dj-site's `isUserIncomplete()` reads only that flag (`hasCompletedOnboarding !== true`); it never re-derives completeness from profile fields. Onboarding-completeness logic — in the app, in a migration backfill, anywhere — must never infer "complete" from `real_name`/`dj_name` presence; a migration 0043 backfill predicate that additionally required a non-empty `dj_name` (which dj-site's `getIncompleteUserAttributes()` treats as optional) drifted from the app's real-`real_name`-only rule and silently stranded ~17 legacy DJs at `/login?incomplete=true` (BS#1451). Any future backfill of this flag must match that real_name-only rule, not invent a new predicate.

## Account-modification audit trail (BS#2537, parent epic #2534)

Every account-modifying request under `apps/auth` writes an `account_audit_event` row: action slug, actor (from the session, never the request body — an audit trail a caller can forge names the wrong person), true HTTP status, and (for ≥400 JSON bodies carrying a string `code`) the typed `error_code`. Post-incident forensics is the primary purpose — "who did it, to whom, when, did it succeed" — not before/after value capture (no payload diffing) and not operational debugging.

**Mechanism**: one Express-layer decorator (`apps/auth/account-audit-middleware.ts`), not a better-auth `hooks.after` (would double-log internal `auth.api.*` calls, e.g. `complete-onboarding`'s `resetPassword`, and is blind to before-hook rejections and 429s) and not a Postgres trigger (no actor at all). It hooks `res.write`/`res.end` (better-call's node adapter — the layer `toNodeHandler(auth)` delegates to — writes response bodies raw, never through `res.json`) for the ≥400 `error_code` capture, and `res.on('finish'|'close')` behind a write-once guard for the log itself, since `finish` does not fire on client disconnect.

**Coverage**: `apps/auth/audit-coverage.ts` is the single source of truth for what is covered and how — the `/auth/admin` prefix (every non-GET, plus a named GET-include list for the PII bulk reads), the `FlatMount` table for a fixed set of exact paths, an `EXPLICIT_CALL_SITES` set for the two mounts a decorator cannot reach (`POST /auth/wxyc/complete-onboarding`'s internal `resetPassword` call, and `jobs/station-signup-review`'s downgrade write), and an `ALLOWLIST` naming every deliberate skip. `apps/auth/app.ts`'s mounts and `scripts/check-audit-route-coverage.ts`'s drift check both import this module, so a mount and the check it is measured against cannot drift from each other. The mount MUST register above every hand-written `/auth/admin/*` route (`resolve-organization`, `provision-user`, the station-signup admin router) — Express dispatches in registration order — pinned by a source-text test (`tests/unit/auth/account-audit-mount-order.test.ts`) rather than by introspecting the running app: Express 5.2.1 removed `app._router`, and `app.ts` runs `app.listen()` at module scope, so the app object cannot be imported under the unit suite.

**Drift enforcement**: `npm run check:audit-coverage` runs `scripts/check-audit-route-coverage.ts` under `tsx`, two arms. Arm 1 runtime-imports the real `auth` object and enumerates `Object.values(auth.api)` — this is why it needs `tsx`, not `jest`: the unit suite maps better-auth to hand-written mocks, so a library upgrade adding a route would be invisible there. Arm 2 sweeps `app.ts`'s source text for hand-written `app.post/put/patch/delete('/auth…')` registrations, since `auth.api` cannot see those. Hard-fail in `.husky/pre-push` (dotenvx-wrapped — importing `auth` pulls `@wxyc/database`, which throws at import without DB env) and in CI's `lint-and-typecheck` job (bare `tsx`, dummy DB env in the step, after the `Type check` step whose `lint:prebuild` builds the `@wxyc/database`/`@wxyc/authentication` dist the import resolves through).

**Known deviation from the original design text**: the design named a flat mount at `/auth/forget-password`. The installed better-auth has no such endpoint — the real "forgot password" route is `POST /request-password-reset` (`app.ts`'s pre-existing `rateLimitedPaths` rate-limits the dead `/auth/forget-password` string, unrelated to this mechanism). `audit-coverage.ts`'s `forget-password` action mounts on the real path.

**Actor / subject resolution**: authenticated mounts call `auth.api.getSession` once before `next()` — resolving before the handler is what attributes `admin/impersonate-user` to the real manager via `impersonatorUserId` (`session.session.impersonatedBy`) rather than the impersonated DJ. Public mounts (no session exists: `forget-password`, `reset-password`, `device/approve`, `device/deny` — the last two mount ahead of the rate limiter alongside the first two, so resolving a session there would be a pre-limit DB-read DoS amplifier) skip actor resolution entirely. Subject is best-effort: a generic `userId` body field by default, the caller's own resolved actor id on self-service mounts (`change-password`, `change-email`, `update-user`, `delete-user`), and — the one DB read this layer performs — an email→id lookup for `forget-password`, gated to 2xx outcomes on that public mount so a distributed brute force cannot buy one `auth_user` read per throttled attempt; the submitted email string itself never lands in the table.

**Failure semantics**: uniform best-effort. `recordAccountAuditEvent` (`shared/database/src/account-audit.ts`) never throws; a write failure reaches Sentry tagged `subsystem: 'account-audit'` via an injected `onError`, and the response the caller sees is never affected — the write happens after `finish`, when there is nothing left to fail closed against.

**Read path**: SQL-only. No endpoint, no UI — "who may read the log" is itself an accountability question nothing currently needs answered.
