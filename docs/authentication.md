# Authentication

The `shared/authentication` workspace package wraps better-auth and provides JWT verification + role-based access control for the API server.

**Key files:**

- `auth.definition.ts` — better-auth config with plugins and hooks
- `auth.roles.ts` — The grant matrix (`WXYC_GRANTS` + `ORG_ADMIN_GRANTS`) and the role construction it feeds
- `auth.middleware.ts` — JWT verification and permission checking
- `auth.client.ts` — Client-side better-auth initialization
- `email.ts` — SES email sending (password reset, verification)

**Roles form a chain** — member < dj < musicDirector < stationManager — but the chain is a **CI-enforced invariant on the grant data, never a runtime mechanism**. `requirePermissions` checks each role's own flat grant set with no fallback to the role below it; the ordering is true because `tests/unit/authentication/auth.roles.test.ts` proves it, not because any code walks it. That distinction is what keeps `flowsheet: ['manage']` meaningful as its own action rather than a proxy for "MD or above".

`@wxyc/shared` owns role _identity and order_ (`ROLES`, `ROLE_ALIASES`, `canonicalizeRole`); this repo owns the **only** grant matrix. Two blocks in `auth.roles.ts`:

- **`WXYC_GRANTS`** — the station domain, typed-total: every role must decide every key (`[]` is an explicit denial), so adding a key to `statement` without deciding it for all four roles is a **compile error**. This replaced the trap where a new key granted to `dj` but left to arrive at `stationManager` via a spread produced a plain DJ with 200 and a station manager with 403.
- **`ORG_ADMIN_GRANTS`** — better-auth's own org-administration keys (`organization`/`member`/`invitation`/`team`/`ac`), held by `stationManager` alone, written out explicitly. It used to be `...adminAc.statements`, which reads as "stationManager gets everything" and is in fact a fixed library-owned set conferring no custom key.

**Permissions per role (station domain):**

| Role           | bin        | catalog    | flowsheet                                     | album_reviews | digital_archive |
| -------------- | ---------- | ---------- | --------------------------------------------- | ------------- | --------------- |
| member         | read/write | read       | read                                          | — (`[]`)      | — (`[]`)        |
| dj             | read/write | read       | read/write                                    | read          | listen          |
| musicDirector  | read/write | read/write | read/write + manage                           | read          | listen          |
| stationManager | read/write | read/write | read/write + manage (plus org administration) | read          | listen          |

`album_reviews: read` gates `GET /album-reviews` (ADR 0011) — the internal surface over the whole DJ form-review archive, without the public `wxycReviews` attach's `social_consent = true` filter, because the form's consent question asked only about social media and internal station tools were never in its scope. The key is deliberately not called `reviews`: ADR 0006 reserves that name for the in-app Review model, a different resource. `member` decides the key as `[]`, an explicit denial rather than an omission; `stripEmpty` drops it before better-auth sees it, so the constructed role is byte-identical to one that never mentioned it.

`digital_archive: listen` gates `GET /digital-archive/albums/:id/playback` (BS#2320) — presigned playback manifests into the auto-DJ Space. Same tier and same `member: []` denial shape as `album_reviews`: the legal boundary is "authenticated DJs", not `catalog: read` (which `member` already holds).

**JWT payload**: `sub` (user ID), `email`, `role` (queried from the organization member table, not `user.role`).

**`requirePermissions` middleware flow:**

1. Extract Bearer token from `Authorization` header via the shared `parseBearerToken` helper — the Bearer scheme is matched case-insensitively per RFC 6750 §2.1 (`bearer`/`Bearer`/`BEARER`), and a bare `Bearer` with no token is rejected with 401. The same helper serves the `AUTH_BYPASS` branch so the two cannot drift (BS#1125).
2. Verify against JWKS endpoint (`BETTER_AUTH_JWKS_URL`)
3. Check issuer and audience claims
4. Resolve the role string through `normalizeRole` → `@wxyc/shared`'s `canonicalizeRole` (403 on `undefined`). This **accepts** more than `WXYCRoles`' literal keys — `admin`/`owner` and case/underscore variants resolve — and **rejects** prototype keys, which the previous `role in WXYCRoles` check let through (`role: 'toString'` resolved and then crashed the middleware with a 500). Stored and emitted role values are always the four station keys; the alias set is read-side only.
5. Check permissions using the role's authorize function
6. 403 if role invalid or permissions insufficient

**Auth bypass**: Set `AUTH_BYPASS=true` to skip JWT verification in tests. Rate limiting is disabled when `NODE_ENV=test`.

**Role mismatch gotcha**: better-auth's organization plugin has built-in roles (`owner`, `admin`, `member`) that overlap with WXYC's custom roles. A `member.role` the alias table can't resolve returns 403 on every request. Organization hooks sync admin-granting roles to `user.role='admin'` for the better-auth admin plugin — via `grantsAdminFlag` (`admin-flag-sync.ts`), which is now the **single** definition of that question. It previously existed as **five** verbatim `['stationManager', 'admin', 'owner']` copies (the grant hook, `hasOtherAdminMembership`'s SQL IN-list, `apps/auth/app.ts`'s boot reconciler `findUsersMissingAdminFlag`, `provision-user.ts`, and a backfill script); the grant path widened with the shared alias table while a hardcoded revocation list would not have, so grant and repair could accept different strings — and the boot reconciler is _specifically_ the retry path for a membership hook that failed, so a narrow copy there meant a membership the hook granted on could never be repaired if the hook died. `hasOtherAdminMembership` therefore filters in TS rather than SQL, and deliberately carries **no `.limit(1)`** — with the role predicate out of SQL, a limit would return one arbitrary membership and a user holding both a `dj` and a `stationManager` row would wrongly lose the flag.

`device-authorization.ts` deliberately does **not** use the alias table: `/device/approve` gates on `Object.hasOwn(WXYCRoles, role)`, so a stray `admin`/`owner` membership row cannot QR-approve a session. That divergence is intentional and commented at the call site.

Prior art: the unmerged `docs/auth-convergence-proposals` branch (2026-02-14) argued that admin is a system axis orthogonal to station roles and that better-auth's built-in org roles should never be _stored_ as WXYC member roles. Both hold here — `admin-flag-sync` implements the first, and nothing in this design stores built-in roles; the alias mapping is read-side normalization for stray or legacy rows only.

**Capabilities (cross-cutting, per-user grants independent of role)**: `auth_user.capabilities` (`text[]`, default `[]`) holds arbitrary capability strings — today `editor`/`webmaster`, granted via `dj-site`'s admin roster page, and `crm_merge` (BS#1884, gating `WXYC/wxyc-crm`'s donor-dedup admin tool). `getAdditionalUserInfoClaim` (`auth.definition.ts`) and the JWT plugin's `definePayload` both emit the array verbatim on the OIDC/JWT `capabilities` claim, with no per-capability-name code change required. There is no dedicated grant endpoint or UI for a capability beyond `editor`/`webmaster` — to grant any capability (including `crm_merge`) to a user, call Better Auth's `admin()` plugin `updateUser` endpoint with `data: { capabilities: [...existingCapabilities, 'crm_merge'] }`, the same call `dj-site`'s `AccountEditForm.tsx` (`updateCapabilities`) already makes in production, run from an authenticated admin session. This is an operator action (a one-off script or `curl` against the admin API), not a `Backend-Service` code path — no schema migration is needed, and `capabilities` is already registered in `additionalFields`. That registration carries `input: false` as of BS#2358, so the array is **not** freely writable: the operator grant path above is unaffected (the `admin()` plugin's `/admin/update-user` hands its `data` object straight to `internalAdapter.updateUser` and never calls `parseUserInput`), but better-auth's public `POST /update-user` can no longer set it. Until that flag landed it could — the route sits behind `sessionMiddleware` only, so any signed-in DJ could grant themselves any capability, `crm_merge` included, and have it emitted on their next JWT/OIDC claim.

**`additionalFields` has two independent gates, `input` and `returned`, and they answer different questions**: `parseUserInput` filters on `input`, so `input: false` stops better-auth's public `POST /update-user` writing a field; `parseUserOutput` filters on `returned`, so `returned: false` stops a field appearing in a response body. A field can be locked against writes and still be emitted on every payload — the two flags are not a pair, and `tests/unit/authentication/pii-additional-fields-input.test.ts` enforces `input: false` as deny-by-default (every field is locked unless it appears in a short, justified `WRITABLE_FIELDS` map) while `returned: false` stays a per-field decision. `returned` is **global, not audience-scoped**: the admin plugin's `/admin/list-users` maps every row through the same `parseUserOutput`, so a field hidden from `/get-session` is also hidden from `dj-site`'s admin roster, and `buildJwtPayload`/`buildOidcUserInfoClaim` spread the whole user object onto the JWT and the OIDC `additional_user_info` claim. Today exactly one field carries the flag: `auth_user.self_signup_reviewed_by` (BS#2358), because it holds _another_ person's `auth_user.id` — the manager who cleared a self-signup review — and without it that id reaches the reviewed DJ and every relying party. The three sibling timestamps `self_signup_at`, `self_signup_reviewed_at` and `self_signup_downgraded_at` deliberately stay returned: `dj-site`'s pending-review predicate is `self_signup_at IS NOT NULL AND self_signup_reviewed_at IS NULL`, read straight off `/admin/list-users`, so hiding either of the first two would silently pin it to a constant — a review queue that never empties, or one that never fills — and hiding the third would leave a manager unable to tell an account `jobs/station-signup-review` auto-downgraded (BS#2364) from one that was always a `member`. None of the three names anyone but the account holder; the downgrade's actor is a cron job, not a person. A "reviewed by ⟨name⟩" display, if it is ever wanted, must come from a `Backend-Service` admin endpoint rather than from re-opening this flag.

**Onboarding completeness is flag-authoritative, not field-derived**: `auth_user.has_completed_onboarding` is the single source of truth for whether a DJ has finished onboarding. dj-site's `isUserIncomplete()` reads only that flag (`hasCompletedOnboarding !== true`); it never re-derives completeness from profile fields. Onboarding-completeness logic — in the app, in a migration backfill, anywhere — must never infer "complete" from `real_name`/`dj_name` presence; a migration 0043 backfill predicate that additionally required a non-empty `dj_name` (which dj-site's `getIncompleteUserAttributes()` treats as optional) drifted from the app's real-`real_name`-only rule and silently stranded ~17 legacy DJs at `/login?incomplete=true` (BS#1451). Any future backfill of this flag must match that real_name-only rule, not invent a new predicate.

## Account-modification audit trail (BS#2537, parent epic #2534)

Every account-modifying request under `apps/auth` writes an `account_audit_event` row: action slug, actor (from the session, never the request body — an audit trail a caller can forge names the wrong person), true HTTP status, and (for ≥400 JSON bodies carrying a string `code`) the typed `error_code`. Post-incident forensics is the primary purpose — "who did it, to whom, when, did it succeed" — not before/after value capture (no payload diffing) and not operational debugging.

**Mechanism**: one Express-layer decorator (`apps/auth/account-audit-middleware.ts`), not a better-auth `hooks.after` (would double-log internal `auth.api.*` calls, e.g. `complete-onboarding`'s `resetPassword`, and is blind to before-hook rejections and 429s) and not a Postgres trigger (no actor at all). It hooks `res.write`/`res.end` (better-call's node adapter — the layer `toNodeHandler(auth)` delegates to — writes response bodies raw, never through `res.json`) for the ≥400 `error_code` capture, and `res.on('finish'|'close')` behind a write-once guard for the log itself, since `finish` does not fire on client disconnect.

**Coverage**: `apps/auth/audit-coverage.ts` is the single source of truth for what is covered and how — the `ADMIN_ACTIONS` map (path -> `{ action, includeGet? }`; a path is covered iff it's a KEY in this map, non-GET by default, with an explicit `includeGet: true` flag on the PII bulk-read GETs — `ADMIN_GET_INCLUDES` no longer exists as a separate symbol, merged into this map by the simplify pass), the `FlatMount` table for a fixed set of exact paths, an `EXPLICIT_CALL_SITES` set for the two mounts a decorator cannot reach (`POST /auth/wxyc/complete-onboarding`'s internal `resetPassword` call, and `jobs/station-signup-review`'s downgrade write), and an `ALLOWLIST` naming every deliberate skip. `apps/auth/app.ts`'s mounts and `scripts/check-audit-route-coverage.ts`'s drift check both import this module, so a mount and the check it is measured against cannot drift from each other. The mount MUST register above every hand-written `/auth/admin/*` route (`resolve-organization`, `provision-user`, the station-signup admin router) — Express dispatches in registration order — pinned by a source-text test (`tests/unit/auth/account-audit-mount-order.test.ts`) rather than by introspecting the running app: Express 5.2.1 removed `app._router`, and `app.ts` runs `app.listen()` at module scope, so the app object cannot be imported under the unit suite.

**Rate limiting (BS#2554, parent epic #2534)**: the whole `/auth/admin` prefix sits behind a dedicated `adminPrefixRateLimit` instance (100 requests/15min/IP, `apps/auth/app.ts`), mounted ahead of BOTH the account-audit prefix mount above and every hand-written `/auth/admin/*` route (`resolve-organization`, `provision-user`, the station-signup admin router). Before this, an anonymous request to a known admin path cost one `auth.api.getSession` read — the audit mount above resolves an actor unconditionally, ahead of any authorization check — plus one `account_audit_event` INSERT, with nothing bounding how often that could happen; registering the limiter first means an over-budget request 429s before either cost is paid. It is its own instance with its own store, never `authMutationRateLimit`'s shared 10/15min bucket: the control room shares one egress IP, so folding admin traffic into sign-in's budget would let routine admin work 429 sign-in for everyone in the building (the PR #2550 lesson). It does not move the audit write behind the authorization outcome — a request inside the budget is still audited on a 401/403 exactly as before; the limiter bounds volume, not which outcomes get recorded, so a recorded probe against `set-role` or `remove-user` stays the forensic signal this trail exists to produce. Sized at 100/15min rather than the tighter 10/15min brute-force tier because the limiter runs ahead of authentication and has to clear the busiest legitimate burst — semester-start provisioning from the control room's one shared egress IP — not just steady-state traffic.

**Rate limiting for the fourteen authenticated flat mounts (BS#2604, parent epic #2534)**: `/auth/change-password`, `/auth/change-email`, `/auth/update-user`, `/auth/delete-user`, and the ten `/auth/organization/*` mutations (`mountAuthenticatedAccountAudit`'s full coverage set) shipped with no rate limiter at all — the same defect BS#2554 fixed for `/auth/admin`, left open on this surface until now. Three dedicated `apps/auth/app.ts` instances, not one shared bucket: `updateUserRateLimit` (60s/60) alone for `/auth/update-user`, since dj-site's `ColorSchemeToggle` calls `authClient.updateUser()` from an undebounced `IconButton onClick` with no reload to self-limit it, unlike the sibling `ThemeSwitcher`/`ThemePicker` controls; `sensitiveAuthMutationRateLimit` (15min/10, `authMutationRateLimit`'s tier) for `/auth/change-password` (a password oracle via `currentPassword`), `/auth/change-email` (sends mail), and `/auth/delete-user` (whose mount also covers better-auth's `/delete-user/callback`, deliberately); and `organizationMutationRateLimit` (15min/100, mirroring `adminPrefixRateLimit`) for the ten organization mutations, mounted as an EXPLICIT path list rather than the `/auth/organization` prefix — that prefix also covers 25 dj-site read call sites (`listMembers`, `getFullOrganization`) that would 429 the roster page for the whole control room. The path-list approach depends on Express 5.2.1's `app.use` matching being segment-aware, verified empirically before relying on it: `create` does not shadow `create-role`/`create-team`, `update` does not shadow `update-member-role`/`update-role`/`update-team`, and `delete` does not shadow `delete-role`. None of the three are folded into `rateLimitedPaths`, and all three register ahead of `mountAuthenticatedAccountAudit(app)` (pinned in `tests/unit/auth/account-audit-mount-order.test.ts`) so an over-budget request 429s before the audit dispatch's `getSession` read and INSERT run. All three numbers come from what the dj-site UI can emit plus margin, not measured load — the live table held 17 rows total across these fourteen paths over two days, only `update-user` among them — so raise a number rather than treat it as settled if a real burst is measured above it.

**Drift enforcement**: `npm run check:audit-coverage` runs `scripts/check-audit-route-coverage.ts` under `tsx`, two arms. Arm 1 runtime-imports the real `auth` object and enumerates `Object.values(auth.api)` — this is why it needs `tsx`, not `jest`: the unit suite maps better-auth to hand-written mocks, so a library upgrade adding a route would be invisible there. Arm 2 sweeps `app.ts`'s source text for hand-written `app.post/put/patch/delete('/auth…')` registrations, since `auth.api` cannot see those. Hard-fail in `.husky/pre-push` (dotenvx-wrapped — importing `auth` pulls `@wxyc/database`, which throws at import without DB env) and in CI's `lint-and-typecheck` job (bare `tsx`, dummy DB env in the step, after the `Type check` step whose `lint:prebuild` builds the `@wxyc/database`/`@wxyc/authentication` dist the import resolves through).

**Known deviation from the original design text**: the design named a flat mount at `/auth/forget-password`. The installed better-auth has no such endpoint — the real "forgot password" route is `POST /request-password-reset`. `audit-coverage.ts`'s `forget-password` action mounts on the real path, and `app.ts`'s `rateLimitedPaths` (which used to rate-limit the dead `/auth/forget-password` string) was fixed to the real path in the same review pass, so the public-mount 2xx-gate argument below actually holds for it now.

**Actor / subject resolution**: authenticated mounts call `auth.api.getSession` once before `next()` — resolving before the handler is what attributes `admin/impersonate-user` to the real manager via `impersonatorUserId` (`session.session.impersonatedBy`) rather than the impersonated DJ. Public mounts (no session exists: `forget-password`, `reset-password`, `device/approve`, `device/deny`, and the three OTP password-reset arms below — all mount ahead of the rate limiter, so resolving a session there would be a pre-limit DB-read DoS amplifier) skip actor resolution entirely. Subject is best-effort: a generic `userId` body field by default, the caller's own resolved actor id on self-service mounts (`change-password`, `change-email`, `update-user`, `delete-user`), and — the one DB read this layer performs — an email→id lookup for `forget-password` and its three OTP-flow twins below, gated to 2xx outcomes on those public mounts so a distributed brute force cannot buy one `auth_user` read per throttled attempt; the submitted email string itself never lands in the table.

**OTP-based password-reset flow (BS#2547, M5 re-decision, parent epic #2534)**: `/email-otp/request-password-reset`, `/email-otp/reset-password`, and the deprecated alias `/forget-password/email-otp` are audited the same way as the token-based `forget-password`/`reset-password` pair above — same public FlatMount partition, same `email-lookup` subject strategy, same pre-rate-limiter position. They do **not** share `rateLimitedPaths`' 10/15min brute-force tier with `forget-password`/sign-in, though: an OTP reset is a hand-copied-code flow, so that shared-bucket, X-Real-IP-only tier would let two DJs resetting before a shift lock out everyone's sign-in from the control room's one egress IP (M3, code review BS#2547). The three paths instead split across two dedicated limiters, sized by actual per-call cost rather than copied wholesale from a no-email donor (M3, corrected on re-review): `request-password-reset` and the `forget-password` alias both call `sendVerificationOTP` — `emailOTP()` sets no `resendStrategy`, so every call sends a real SES email with no internal cooldown — so they get the SAME 10/15min tier as the identical-cost token flow above, on their own limiter instance (never folded back into `rateLimitedPaths`, which would re-couple them to sign-in). `email-otp/reset-password` sends nothing and is already attempt-bounded server-side (`allowedAttempts: 5` in the `emailOTP` plugin config), so it gets a looser 60s/30 sized for hand-entry across a shared control-room IP. Either way the email-lookup DoS argument above still holds — every path still sits behind an Express-layer limiter ahead of its `auth_user` read. Path-derived dotted action slugs (`email-otp.request-password-reset`, `email-otp.reset-password`, `forget-password.email-otp`) are deliberately distinct from the token flow's `forget-password` slug, so a forensic query can tell which flow a DJ actually used — note that `forget-password` and `forget-password.email-otp` ARE distinct flows despite the shared prefix, so a query for "every forget-password-flow row" needs `action IN ('forget-password', 'forget-password.email-otp', ...)`, never a `LIKE 'forget-password%'`, which would also match `forget-password.email-otp` under a name that reads as the same flow but isn't; the two `email-otp.*` request slugs are likewise distinct actions, so counting "how many OTP reset requests" needs the same `IN (...)` form, not a single slug. These three were allowlisted at ship time (code review BS#2537 PR #2545, finding M5) with a comment marking the hole as needing an explicit re-decision; the re-decision (2026-09-17) is "audited". The **email-change** OTP variants — `/email-otp/change-email`, `/email-otp/request-email-change` — have the same live-and-unaudited shape but are explicitly **not** covered by this re-decision and remain allowlisted pending one of their own.

**Body-discriminated mount — `/email-otp/send-verification-otp` (BS#2551, Option A, parent epic #2534)**: M2 of the BS#2547 code review flagged this endpoint as an unaudited twin of the request step above — called with `type: 'forget-password'` it runs the identical `resolveOTP(..., 'forget-password')` path and mails the same working reset code, but it ALSO serves the deliberately-out-of-scope sign-in OTP flow (`type: 'sign-in'`, every current WXYC client's real traffic here) and the never-in-scope `type: 'email-verification'`, discriminated by one `type` body field. `FLAT_MOUNTS`'s path-keyed table couldn't express "audit this path only for one body value" — auditing the whole path would have widened the ratified scope (sign-in/sign-up stay out) and added high-traffic rows to a table whose two-composite-index choice is justified on staying small. BS#2551 resolved this by extending `FlatMount` itself: a mount now carries EITHER a static `action` (decision 14's plain path-derived slug, every other mount) OR a `discriminator: { field, actions }` (a request-body field name plus a value → action-slug map). `classifyFlatMountAction(mount, body)` — pure, unit-tested, co-located with the table in `audit-coverage.ts` — resolves a discriminated mount's runtime action; a body value absent from `actions` (including a missing or non-string field) classifies to `null`, and `account-audit-middleware.ts`'s `flatMountAuditMiddleware` treats a `null` classification exactly like M2's admin-prefix unknown-path gate: skip before any work, write nothing. `/email-otp/send-verification-otp`'s own entry maps only `'forget-password'`, so a `type: 'sign-in'` or `type: 'email-verification'` call records zero rows while `type: 'forget-password'` records one with the same `email-lookup` subject strategy (2xx-gated, never persists the raw email) every other reset mount uses.

The recorded action is `email-otp.send-verification-otp.forget-password`, not the bare path-derived `email-otp.send-verification-otp` — decision 14's convention extended one dot further with the discriminated value, the same "path prefix + variant suffix" shape `admin.station-signup.<op>` already uses (there the suffix is a literal path segment; here it comes from the request body, since the variant isn't reachable as its own path). This keeps the slug self-explanatory without requiring a reader to already know the discriminator exists, and keeps it distinct from the sibling `email-otp.request-password-reset` action even though both endpoints run the same underlying `resolveOTP` call and are, for a DJ, functionally interchangeable reset requests — collapsing the two slugs together would recreate the exact "who requested this reset code" ambiguity M2 complained about, just one level removed.

All three drift-check arms stay meaningful under a conditionally-audited mount: arms 1 (`findUncoveredAuthApiEndpoints`) and 3 (`findDeclaredMountsMissingFromAuthApi`, the reverse arm) both reason PATH-ONLY — `isFlatMounted` checks membership by `.path`, never which values a `discriminator` maps — so this path is "covered"/"still reachable" exactly like a static mount: the classification has been reviewed and encoded, not "every request through it writes a row" (a claim arm coverage never made even for a static mount, given the public-mount 2xx-only subject gate). Arm 2 is blind to `FLAT_MOUNTS` internals entirely and is unaffected. `/email-otp/send-verification-otp` moved OUT of `ALLOWLIST` as part of this change — it is no longer a deliberate skip, it is a `FLAT_MOUNTS` row like any other, just one whose action depends on the request.

Rate limiting was deliberately left untouched: the path stays in `app.ts`'s shared `rateLimitedPaths` (`authMutationRateLimit`, 15min/10) rather than moving to the `otpPasswordResetSendRateLimit` instance PR #2550 introduced for the two other email-sending reset mounts. The two tiers are numerically identical (15min/10) — there is no looser-bucket hazard here the way there was for the dedicated reset mounts pre-#2550 — and every real call to this endpoint today carries `type: 'sign-in'`, so the shared-with-sign-in bucket is bucketing the traffic it actually has. Splitting it to isolate the newly-audited-but-currently-unreachable `forget-password` variant would need a new mechanism (peeking `req.body.type` before selecting a limiter instance) this ticket's scope didn't call for; revisit if forget-password traffic through this endpoint ever becomes real.

**Failure semantics**: uniform best-effort. `recordAccountAuditEvent` (`shared/database/src/account-audit.ts`) never throws; a write failure reaches Sentry tagged `subsystem: 'account-audit'` via an injected `onError`, and the response the caller sees is never affected — the write happens after `finish`, when there is nothing left to fail closed against.

**Read path**: SQL-only. No endpoint, no UI — "who may read the log" is itself an accountability question nothing currently needs answered.
