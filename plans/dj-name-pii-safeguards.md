# DJ real-name PII safeguards — end the `name` / `dj_name` conflation

## Problem

WXYC collects DJs' full legal names as a legal requirement. That collection is correct and stays. The failure class is **conflation**: commit `a0cd1979` (2025-12-31) collapsed the old `djs` table's two-column design (`dj_name` handle / `real_name` PII) into `auth_user` and introduced `djName || name` fallbacks, while dj-site provisioning fills `auth_user.name` with `realName || username` (`RosterTable.tsx:92`). From then on, `auth_user.name` — better-auth's innocuously-named, required display field — has been a **hidden second copy of the legal name**, and every innocent-looking `.name` read is a potential PII leak to a public surface. BS#1286/#1288, `2a37bbc6`, BS#1393, and BS#2281 are all downstream of that one structural fact.

This plan is the prevent-recurrence layer. The stored-data remediation (`jobs/flowsheet-dj-name-scrub`, BS#2281, branch `fix/2281-dj-name-scrub`) is a separate, already-planned track and is not re-planned here.

Decisions already made by the maintainer (2026-08-27):

- **No wire rename.** `flowsheet.dj_name` keeps its name across api.yaml/clients; semantics are fixed and enforced instead. (The originally-requested `dj_name → dj_real_name` rename was based on an inverted mapping — `dj_name` columns hold the _handle_; the PII hides in `auth_user.name` — and was withdrawn on correction.)
- **`auth_user.name` := on-air handle, else username.** Public-safe by construction: after the unscrew, even an accidental `.name` read leaks nothing.

## Facts (verified 2026-08-27, evidence at file:line)

- The duplicate is injected at exactly one place: dj-site `RosterTable.tsx:92` sends `name: newAccount.realName || newAccount.username`; the auth provision route (`apps/auth/app.ts:270` → `provision-user.ts:114`) stores the client-supplied `name` verbatim. **`name` is in the route's required-fields validation** (`app.ts:261`) and non-optional in `ProvisionUserInput` (`provision-user.ts:34`).
- `auth_user.name` is **written once and never maintained**: roster edits (`AccountEditForm.tsx:223`) call better-auth's `authClient.admin.updateUser` **directly against the auth service — that request never passes through any Backend-Service call site** — and update `realName`/`djName` without touching `name`; onboarding (`complete-onboarding.ts`) likewise. The PII copy also goes stale.
- Exactly **one live serving-path reader** of `auth_user.name` remains: `shared/legacy-mirror/src/http-mirror.ts:512` (`djHandle = override || dj.djName || dj.name`) — the fifth writer `2a37bbc6`'s "all four writers" missed. It writes real names into tubafrenzy's public `DJ_HANDLE` field for handle-less DJs **today**. Line `:514` (`djName: dj.realName || dj.name`) is the _legitimate_ legal-name flow to tubafrenzy's `DJ_NAME` field. The call site (`flowsheet.mirror.ts:163`) selects the full `user` row, so `username` is already in hand; `MirrorDJ` (`http-mirror.ts:491`) needs one optional field. `shared/legacy-mirror` already depends on `@wxyc/database` (its `rotation-match.ts:53` imports from it), and `dj-name.ts` is re-exported at `shared/database/src/index.ts:21`.
- dj-site reads `realName` explicitly in its roster components and `LeftbarLogout.tsx:26`, **but is NOT clean**: `lib/features/admin/conversions-better-auth.ts:27-28` reads `userName: user.username || user.name` and `realName: user.realName || user.name || "No Real Name"` (feeding the roster's Real Name column), and `lib/features/authentication/utilities.ts:140,169,229,258` maps `session.user.name` onto dj-site's `User`. After 2d these fallbacks would show a handle under a "Real Name" label wherever `real_name` is still empty — 2a bounds that class (it populates `real_name` everywhere `name` held a legal name), but the fallbacks must be dropped, not merely outrun. An earlier draft claimed dj-site "renders `user.name` nowhere"; that grep covered `src/` only and missed `lib/`.
- Other `name` writers: `create-auto-dj-user.ts:80` (`'Auto DJ'`), the better-auth anonymous plugin (`'Anonymous'`). Both non-PII; both must survive the derivation hook unclobbered.
- better-auth requires `name` NOT NULL; `realName`/`djName` are `additionalFields` (`auth.definition.ts:618-620`). **`databaseHooks.user` already exists** (`create.after` at `:521-524`; a working `before`-hook precedent at `:588`), so a before-hook pair is an established extension point, not a new pattern.
- `auth_user.username` is nullable in schema, but every provisioned user has one (provision route requires it); anonymous users lack one and keep `name='Anonymous'`.
- Custom-lint precedent: `eslint-rules/no-bare-array-in-sql-template.cjs`, `source-tagged-constraint.cjs`, registered via the merged `wxycLocalRules` object (`eslint.config.mjs:11-16`), with rule tests at `tests/unit/database/*.rule.test.ts`. **The flat config globally ignores `**/*.js`/`**/*.cjs`/`**/*.mjs` and `scripts/**`** (`eslint.config.mjs:19-38`), so `.spec.js` integration tests and one-shot scripts are structurally outside any lint rule's reach.
- Integration tier is `.spec.js` (babel-jest, `jest.config.json`, `--runInBand`, Docker DB via `npm run db:start`); the TS fixtures under `tests/fixtures/` are unit-tier and not directly importable there.
- `apps/backend/app.yaml` is Swagger-UI documentation only; `wxyc-shared/api.yaml` is the schema-first source of truth (CLAUDE.md:196). The `real_name`-bearing `NewDJ` schema (`app.yaml:151-158`, with `cognito_user_name`) hangs off `/djs/register` paths whose router entries `a0cd1979` deleted — dead Cognito-era spec.

## Track 0 — stop the live writer (ships first, alone)

`http-mirror.ts:512`: `djHandle` becomes `override → resolveDjDisplayName(dj.djName ?? null) → username`, importing the canonical helper from `@wxyc/database` — never `name`, never `realName`, never a locally re-derived chain (`dj-name.ts:1-13`). The `?? null` coercion is pinned here, not left to discovery: `resolveDjDisplayName` is typed `(djName: string | null)` and `MirrorDJ.djName` is optional under the package's `strict: true`, so the bare call does not compile — and a type error at exactly this line is the classic pressure to "just inline the trim" and quietly re-derive the chain.

- `username` is the terminal fallback because tubafrenzy's `DJ_HANDLE` round-trips into `shows.legacy_dj_name` via the ETL and displays publicly on wxyc.info; username is the least-surprising non-PII stable identifier, and it matches the chosen `auth_user.name` policy. Add `username?: string | null` to `MirrorDJ`.
- Line `:514` is **left as-is in Track 0**: it targets tubafrenzy's legal-name field, and `realName || name` remains correct _while `name` still duplicates the real name_. It flips to `realName`-only in Track 2d — or dies with the mirror at the 2026-08-31 turndown, whichever comes first.
- **Also in this PR**: correct the `shows.legacy_dj_name` docblock at `schema.ts:2497-2510`, which states the mirror forwards `realName || name` — this PR falsifies that sentence, and a stale doctrine comment on exactly this column is how the last incident propagated.
- Yes, the mirror has ~4 days to live. Still worth shipping: it stops ongoing real-name writes into data the final tubafrenzy dump scrub (BS#1543) must otherwise chase, and stops growing the misattributed share of Cohort C.
- **All-absent behavior, pinned**: when override, handle, and `username` are all missing, `djHandle` becomes `''` — matching the same payload's `showName ?? ''` convention. In practice unreachable (every provisioned user has a username, and anonymous users cannot own shows); the pin exists so the behavior is chosen, not emergent `undefined` on a field tubafrenzy treats as required.
- **This PR also rewrites the `mapShowToTubafrenzy` describe block in `tests/unit/middleware/legacy/http.mirror.test.ts`** — its `:999-1007` case (`'falls back to name when realName/djName are null'`, asserting `djHandle === 'kate'` from `dj.name`) pins exactly the behavior this PR removes; it is the only one of the six `djHandle` assertions that breaks, and becomes the negative case: `djHandle` falls to `username`, never `name`.
- **Second caller covered**: `jobs/legacy-mirror-reconcile/orchestrate.ts:285` also calls `mapShowToTubafrenzy`; its `selectDj` (`:950-953`) selects the full row, so `username` is available there without a query change — update `tests/unit/jobs/legacy-mirror-reconcile/orchestrate.test.ts` fixtures alongside.
- Unit test: `mapShowToTubafrenzy`'s `djHandle` never equals a sentinel planted in `name`/`realName`, across the override/handle/username/all-absent matrix.

## Track 2 — unscrew the data structures (ask 4)

Ordering inside this track is load-bearing: **preserve before overwrite**.

- **2a. Preserve-first.** Some users may hold their legal name _only_ in `name` (`realName` was optional at provisioning). Before `name` is ever rewritten: audit with a SELECT (per the org data-safety rule), then copy `name → real_name` for rows where `(real_name IS NULL OR trim(real_name)='') AND NOT is_anonymous AND name NOT IN ('Anonymous','Auto DJ') AND name IS DISTINCT FROM username`. ~139 roster rows; reviewed manual SQL with the SELECT evidence attached to the issue. Never the reverse direction. Losing a legal name here is the one unrecoverable failure in this plan.
- **2b. One choke point: `databaseHooks.user` before-hooks** in `auth.definition.ts` (extending the existing `databaseHooks.user` block at `:521`), designed around a verified constraint: better-auth's hook runner invokes `toRun(data, context)` (`with-hooks.mjs:53`) and `internalAdapter.updateUser` puts the user id **only in the `where` array the hook never receives** (`internal-adapter.mjs:518-527`) — so an `update.before` hook cannot fetch the row it is updating, and `complete-onboarding.ts:117` calls `internalAdapter.updateUser` outside any better-auth endpoint, so a request-context fallback is unavailable there either.
  - `create.before`: full payload is present — derive `name := resolveDjDisplayName(djName) ?? username ?? <supplied name>`; the supplied-name terminal keeps `'Anonymous'` and `'Auto DJ'` intact.
  - `update.before`: **payload-only derivation, no row fetch needed.** Implemented as a pure helper `deriveUserDisplayName(data) => { data: { name: string } } | undefined` in `shared/authentication/src/`, mirroring `capSessionUpdateAgainstDeviceFlow` (`device-authorization.ts:88-97`) — the return shape is load-bearing, not style: `with-hooks.mjs:53-58` merges **only** a returned `{ data: {...} }`; a mutated argument or bare object is silently discarded and `false` aborts the write, so an unpinned contract fails as a silent no-op. When the update carries a `djName` that resolves to a usable handle, return `{ data: { name: handle } }`; otherwise return `undefined` and `name` stays untouched. Clearing a handle — or renaming a `username` on a handle-less user (the username plugin writes through the same `updateWithHooks` path, and a username-only payload cannot reveal whether a handle exists, so deriving from it risks clobbering a handle) — leaves `name` at its prior value: post-backfill that can only be an earlier handle or an earlier username, so the staleness is cosmetic and structurally non-PII in both cases. This deliberately rejects the alternative (an admin-route-scoped hook plus per-call-site derivation in `complete-onboarding.ts`), which would re-scatter the invariant across N writer sites — the exact disease this track exists to cure. The hook payload's `djName` is untyped at the boundary; the helper coerces `?? null` before calling `resolveDjDisplayName`, same as Track 0.
  - This single site covers `provision-user.ts`, `create-default-user.ts`, `create-auto-dj-user.ts`, `complete-onboarding.ts` (its `internalAdapter.updateUser` call still flows through `updateWithHooks`), **and dj-site's direct `admin.updateUser` roster path** — which no BS call-site helper can reach. Unit tests drive the hook functions directly across the writer matrix, including handle-set, handle-clear (name untouched), and anonymous/service-account create.
  - **Version-skew checkpoint**: `shared/authentication/package.json` declares `^1.6.30` while `1.6.26` is installed; re-verify the hook invocation shape against whatever version the lockfile resolves at implementation time before relying on it.
- **2c. Provision route stops trusting client `name`** — two named edits, since `name` is currently _required_: drop `'name'` from the `app.ts:261` required-fields array and make it optional in `ProvisionUserInput` (`provision-user.ts:34`); `provisionUser` itself supplies the derived value (`resolveDjDisplayName(djName ?? null) ?? username`) and the `create.before` hook overrides it — belt and suspenders, because better-auth's adapter `transformInput` enforces the core schema's `required: true` on `name` and **whether the hook merge runs before that check is unverified against the lockfile-resolved version**; supplying the value at the call site removes the ordering dependency entirely. Also: omit the key rather than spreading `name: undefined` — a present-but-undefined key and an absent key can differ under that validation. Accept-and-ignore a still-supplied `name` for one deploy overlap; test asserts a `name`-less provision body succeeds. dj-site then drops the field from `RosterTable.tsx:92`'s payload (cross-repo PR).
- **2d. Backfill existing rows**: `name := resolveDjDisplayName(dj_name) ?? username`, skipping anonymous users and `'Auto DJ'`; rows with neither handle nor username are left unchanged. Lives at **`jobs/auth-user-name-backfill/`** with `"job-type": "one-shot"` per `docs/migrations.md:62-64` (the same home as `flowsheet-dj-name-backfill` / `legacy-dj-name-remediation`) — the real reason for a full `jobs/` workspace over a `scripts/**` one-off (which 139 rows alone would not justify) is that the **precondition gate wants a testable, reviewable, CI-typechecked entry point**; lint reachability is a side benefit, since 3a allow-lists this job anyway. The workspace is five artifacts, not a directory (deploy-base builds `Dockerfile.${target}` from the repo root and reads `jobs/$TARGET/package.json`): `package.json` (`"job-type": "one-shot"` **and** a `docker:build` script), `tsconfig.json`, `tsup.config.ts`, root `Dockerfile.auth-user-name-backfill`, and the `package-lock.json` entry a new workspace moves — **plus a `Type check: auth-user-name-backfill` step in `.github/workflows/test.yml`** (the BS#2009 precedent at `:221-233`: `npm run typecheck` excludes `jobs/**` and `tsup --minify` is transpile-only, so without the step the job carrying the precondition gate could ship uncompiled-but-green — the worst possible place for that gap). **Opens with a machine-enforced precondition gate**: before writing anything, the job runs 2a's own predicate (`(real_name IS NULL OR trim(real_name)='') AND NOT is_anonymous AND name NOT IN ('Anonymous','Auto DJ') AND name IS DISTINCT FROM username`) and aborts non-zero if any row matches — the `docs/backfill-precondition-assertions.md` pattern from the canonical 0053 → backfill → 0054 chain. Sequencing prose said 2a runs first; this gate makes the legal-name-loss failure impossible regardless of run order, which "the one unrecoverable failure in this plan" deserves. Uses the canonical helper — not SQL re-derivation — with dry-run default and SELECT-scoped evidence. ~139 rows. Then flip mirror `:514` to `realName`-only (safe once 2a has run) **and drop `name` from `MirrorDJ` entirely** — at that point it is a required field with zero readers, still fed by both callers' full-row `select()`, and a reachable-but-unread `name` on the mirror shape is exactly how the fifth writer stayed invisible — unless the turndown has already deleted the call site.
- **2e. Session blast radius — dj-site PR is required, not optional.** Drop the `|| user.name` fallbacks at `conversions-better-auth.ts:27-28` (both `userName` and `realName` conversions; the Real Name column shows `real_name` or its explicit placeholder, never a fallback through `name`) and review `authentication/utilities.ts`'s `session.user.name` mappings — after 2d those carry the handle/username, which is the intended display semantics there. **wxyc-dj-ios and wxyc-dj-android must still be checked** for session-`name` renders (cross-repo tickets). Grep BS email templates for `user.name` during implementation.

## Track 3 — enforcement mechanisms (ask 3)

- **3a. ESLint rule** `wxyc/restricted-real-name` (modeled on the two existing rules): flags `realName` / `real_name` as **both** member-expression access and object-literal property keys (either alone misses half the read/write sites), outside a config allow-list. **No `user.name` clause** — the incident shape is alias-bound (`dj.name` at `http-mirror.ts:512`; both call sites bind the row to a local named `dj`), an identifier-keyed matcher catches none of it, and `name` is a column on at least three tables so a bare `.name` matcher is unusably noisy; that half of the problem is closed by Track 0 and policed by the sentinel spec, and claiming lint coverage the rule cannot deliver is exactly the false-assurance failure this plan indicts elsewhere. Scoped `files: ['apps/**/*.ts', 'shared/**/*.ts', 'jobs/**/*.ts']`, registered in the merged `wxycLocalRules` object (`eslint.config.mjs:11-16`), rule test at `tests/unit/database/restricted-real-name.rule.test.ts`. **`tests/**` stays outside the rule's `files` scope** — precedent: `source-tagged-constraint`'s narrow scoping at `eslint.config.mjs:68` (`shared/database/**/*.ts` only); note `no-bare-array-in-sql-template` at `:103` deliberately _includes_ tests, so the exclusion here rests on its merits — at least seven unit fixtures legitimately construct `realName` objects, per-file allow-list entries for them would rot, and a fixture literal cannot reach a wire (the sentinel spec covers what tests could leak). Allow-list, explicit: `apps/auth/app.ts`, `apps/auth/provision-user.ts`, `apps/auth/create-default-user.ts`, `apps/auth/complete-onboarding.ts`, `apps/auth/create-auto-dj-user.ts`, `shared/authentication/src/auth.definition.ts` (the `additionalFields` declaration at `:619` is a permanent object-literal site) plus the new hook-helper file, `shared/legacy-mirror/src/http-mirror.ts` (until turndown), `shared/database/src/schema.ts` (the `real_name` column definition, `:59`), and `jobs/auth-user-name-backfill/`.
